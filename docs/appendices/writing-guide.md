# 写作与证据规范

每篇包含问题、机制、完整条件、例子、局限与引用入口，解释为什么和如何，避免只列产品。

引用结论限定论文和场景；架构用“建议”“参考”；实测附配置与日志。未经运行不得写已实现或虚构百分比。Atlas 情节均为合成。

来源、证据、信息对象、检查点和派生物保持一致定义。有效时间与记录时间分开，默认区间左闭右开，未知结束为 null。删除与失效不同。

Mermaid 邻近文字解释箭头。语法检查不等于视觉布局审查。模型调整先改术语与契约，再修受影响章节。

引用靠近所支持陈述，文献索引说明核验范围和日期。仅核验摘要不宣称完整复现，不复制第三方整图。

区分两种日期：「资料核验日期」指对外部论文、标准与源码完成核对的日期，只在真正重新核验后更新，不得随修订自动刷新；「最后修订日期」指正文发生实质性修改的日期，仅更正错别字、调整引用页脚等不触发更新。篇首标注的是资料核验日期；修订记录集中写入 CHANGELOG，不在每篇文章内维护。

首稿表示有完整可读论述，不代表经过同行审稿。待研究方向进路线图，不用空段落冒充覆盖。

## 正文编辑标准

从具体问题进入，解释输入、判断依据、处理过程和结果。概念定义应说明与易混概念的差别，以及差别如何影响系统行为。案例、源码和必要的数据快照放在对应机制中，用来解释动作和取舍；运行代码不是正文质量的替代标准。

不要求每篇固定设置推导、案例、局限和自测栏目。有用推导融入它所解释的小节，边界说明紧跟具体方案；只有结论的案例和可以贴到任意文章的阅读问题应删除。失败过程、例外和方案的适用条件都要具体说明。

源码依据限定版本和实际调用路径，区分源码确认、教学推演、参考设计和实测。局部示例只支持其真实验证范围。篇幅和覆盖数量不是验收依据，链接和 CI 通过也不证明讲解已经充分。

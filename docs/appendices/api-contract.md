# API 参考契约与模块协作

> 参考设计，没有在线端点或 SDK。下文用一次规则更正串联接口语义，JSON 仅为说明示例。

## 先确定谁在调用

认证层提供 tenant_id、principal_id、角色和授权范围。请求体中的 requested_scope 只表达希望访问哪个项目，不会授予权限；服务先核对调用者资格，再处理目标对象。

例如 u2 在请求中填入 u1，并不能据此读取 u1 的私有偏好。未知或不可见对象对外统一使用不泄露存在性的错误；所有读取仍检查当前权限和删除状态。读取、修改、删除、写记忆与保存检查点是不同能力，真实发布动作还需业务系统单独授权。

## 一次更正从提交走到可检索

假设规则当前为 v2，调用者希望创建后继 v3。以下状态演变是设计推演，未调用真实服务。

### 1. 首次提交：明确修改前提

调用 POST /v1/items/{id}/revisions，提交新内容、证据和 expected_version=2，并在请求头带 Idempotency-Key=r42。

expected_version 表示“这次修改基于 v2”。服务确认当前仍为 v2 后，以受控事务创建 v3、保存该请求结果，并登记后续索引任务 j3。若提交成功，返回 201、对象版本和任务身份；这只承诺主记录已提交，不表示索引已经可查。

### 2. 响应丢失：确认是否已执行

如果提交后连接中断，客户端不知道服务器是否成功，应携带相同键 r42 和相同请求内容重试。在约定的幂等保留窗口内，服务返回已保存的结果，不再创建一个版本。

服务按租户、操作与幂等键识别请求，并保存请求内容的哈希。同一键换成另一份内容会返回 409 IDEMPOTENCY_CONFLICT，防止新意图误用旧回执。幂等窗口由部署约定，窗口外不能继续假定旧键一定能去重；结果未知时应核对对象状态。

### 3. 并发修改：旧前提不能直接覆盖

另一请求 r43 同样基于 v2，但 v3 已提交。它没有重复执行，却仍不满足版本前提，应返回 409 VERSION_CONFLICT。调用者重新读取 v3，比较并决定合并、放弃或提交新修改，不能只把预期版本改为 3 后原样覆盖。

因此幂等键识别“是否同一次请求”，预期版本检查“这次请求的编辑前提是否仍成立”。两者需要分别保留。

### 4. 索引失败：重试任务，不重新创建业务对象

主记录与待发送任务同事务保存，常称为事务发件箱模式（outbox）。后台投递器读取 j3，再由消费者更新索引。任务记录包含事件身份、对象身份和版本、事件结构版本、发生时间及追踪标识，用于去重、版本核对和诊断。

消费者失败时记录原因并按策略重试；连续失败达到约定上限后进入人工可检查的失败任务队列，通常称为死信队列。任务成功后记录确认，调用者通过 GET /v1/jobs/{id} 查看进度。

如果重试时对象已变为 v4 或已删除，j3 不能把旧内容重新发布为当前结果。只登记任务不保证每个外部动作恰好执行一次，消费者仍需幂等、回查及发布条件检查。

## 删除：受理与清理完成分开

调用 DELETE /v1/items/{id} 时提交预期版本和幂等键。服务先建立在线阻断，使目标不再用于新访问，再返回 202 和删除任务身份。索引、摘要与缓存随后分别清理。

| 状态 | 含义 | 调用者可确认什么 |
| --- | --- | --- |
| accepted | 请求已受理，在线阻断已生效 | 目标不再用于新的在线访问，副本尚待清理 |
| running | 正在处理约定副本 | 可查询逐项进度 |
| partial_failure | 部分副本清理失败 | 在线阻断仍在，未完成项需重试 |
| completed | 约定的在线存储已确认清理 | 不代表保留中的备份已经物理擦除 |

约定存储的清单须由部署明确。备份清理期限和恢复时重放删除记录单独报告，不能用一个 completed 隐藏剩余责任。清理失败也不能撤掉在线阻断。

## 构造本次上下文

POST /v1/context 根据任务读取材料，返回采用的对象、证据和缺口。下面请求只要求解释规则，尚未调用实时审批工具。

~~~json
{
  "query": "只有一人审批，可以普通发布吗？",
  "as_of": "2026-11-03T00:00:00Z",
  "requested_scope": {
    "kind": "project",
    "id": "atlas"
  },
  "token_budget": 5000
}
~~~

token_budget 是**材料预算**：仅限制接口返回并供装配的规范、记忆、工具结果等材料。调用方已扣除系统与工具定义、问题及固定任务字段，并预留输出，接口不重复扣除。

沿用[正文预算示例](../05-retrieval-context/04.md)：本次总额度 8,000，输出预留 1,500，固定输入 1,500，材料预算就是 5,000。额度是手算示意；实际按目标模型的计数方式核对格式开销和各项上限。调用方在新增工具结果或下一轮前重新计算。

响应示例：

~~~json
{
  "schema_version": "1",
  "trace_id": "demo-trace",
  "items": [
    {
      "id": "rule",
      "version": 2,
      "evidence_ids": ["ev-rule-v2"],
      "content": "普通发布需两名审批者。"
    }
  ],
  "missing": ["实时审批状态需业务工具核验"],
  "conflicts": [],
  "truncated": false
}
~~~

这里可以解释“两人审批”的要求，不能确认当前审批是否完成。missing 标明未取得的必要信息，conflicts 列出未决冲突，truncated 表示是否因材料预算排除了候选。无法容纳必要规则时，同时报告缺口，不截断数值、否定或例外后冒充完整材料。

调用方按材料身份安全装配，不把来源文字当成控制指令。部分材料可用时，可以成功返回这些材料及缺口；不能把依赖服务失败包装成资料完整。

## 接口速查

| 操作 | 关键输入 | 输出与承诺 |
| --- | --- | --- |
| POST /v1/items | 候选、证据、幂等键 | 201 主记录版本，索引任务单列 |
| POST /v1/items/{id}/revisions | expected_version、修订、证据、幂等键 | 201 后继版本；版本冲突不覆盖 |
| POST /v1/search | 查询、类型、范围、时点、limit | 候选和排名，不承诺均可作为依据 |
| POST /v1/retrieve | 查询、用途、时点 | 授权有效证据与冲突 |
| POST /v1/memories | 主体、用途、内容、来源、幂等键 | 策略结果与对象版本，可能待审核 |
| POST /v1/context | 任务、范围、时点、材料预算 | 材料清单与 missing、conflicts、truncated |
| DELETE /v1/items/{id} | expected_version、幂等键 | 202 删除任务；在线阻断先于响应生效 |
| GET /v1/jobs/{id} | 任务 ID | 逐项进度、失败和重试原因 |
| PUT /v1/runs/{id}/checkpoint | expected_version、游标、副作用、幂等键 | 新检查点版本，不从经验摘要恢复 |

表中的幂等键均指 Idempotency-Key。所有写入检查真实权限；批量及并发请求还需在实现中保护请求身份与结果记录的唯一性。

## 错误怎样指导下一步

| 错误 | 含义与处理 |
| --- | --- |
| 400 INVALID_INPUT | 修复结构或约束错误，不原样重试 |
| 404 NOT_FOUND_OR_NOT_VISIBLE | 不区分不存在与不可见，不尝试绕过权限 |
| 409 VERSION_CONFLICT | 重新读取并判断修改意图 |
| 409 IDEMPOTENCY_CONFLICT | 同键内容不符，核对是否误用请求身份 |
| 422 INSUFFICIENT_EVIDENCE | 确定结果缺少依据，补充来源或缩小请求 |
| 429 RATE_LIMITED | 按服务约定退避，不改变原请求意图 |
| 503 DEPENDENCY_UNAVAILABLE | 依赖不可用，先核对提交状态，再按幂等约定恢复 |

这些错误码是本项目的参考约定。响应带 schema_version 与 trace_id，错误带 code 和可理解的 message，不暴露内部堆栈或隐藏对象。

新增可选字段需要客户端允许忽略未知字段，且不改变既有语义；字段删除、预算口径等含义变化应通过新主版本及迁移说明处理。本项目尚无运行服务，此处是在明确首版草案的含义，不声称已完成线上协议迁移。

# 8.7 典型应用场景

> 概念说明与参考设计，非已实现系统报告。资料核验日期：2026-11-13。

## 要解决的问题

典型场景的成功标准有什么不同？

场景决定信息价值、错误代价和评测单位。共享底座不意味着采用同一保存策略或统一成功指标。

### 8.7.1 企业知识问答系统

企业问答重点验证有效规范、引用与跨部门权限。用旧版更相似、例外分散和用户退出项目等用例，检查系统能否正确选择与拒答。

评价不仅看文字流畅，还看人数、角色、时点和证据是否一致。规范负责人应能回查来源并更正，而不是只能修改一段最终提示。

### 8.7.2 AI Coding Agent

Coding Agent 需要区分项目惯例、当前工作区状态和历史经验。测试两个项目使用不同命令、分支或依赖时，是否把旧项目方法误用到当前任务。

记录文件和提交快照、工具实际结果及验证范围。模型声称测试通过不能替代当前运行证据；检索到的操作步骤也不能自动获得执行权限。

Letta Code 的已提交核心投影与工作区按需读取使快照差异成为可测试问题。实验必须记录提交 ID、工作区状态和工具读到的文本；答案中出现正确命令，仍需排除模型凭先验猜中的可能。此处是验收设计，不声称已跑过完整 Agent。[R15][固定版本源码](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L65-L198)。

### 8.7.3 长期运行的任务 Agent

长期任务重点是恢复、外部动作确认和目标版本变化。中断后检查任务是否从正确位置继续、是否重复副作用，以及是否重新核对当前权限与业务条件。

自然语言摘要有助解释，却不能替代精确游标和账本。任务最后成功仍可能执行重复操作，验收应逐项核对不变量。

一个必要场景是远端文档已创建、本地确认前中断。重启后若直接创建第二份，即使任务最终显示成功，恢复也不正确。验收应核对目标对象身份、动作次数及确认记录；恢复应按幂等键或远端查询确认，再推进游标。历史经验可以提示采用这个方法，但真正恢复仍依赖本次运行的精确状态。

### 8.7.4 个人知识管理系统

个人知识管理关注来源组织、偏好更正、历史解释和撤回。用户应能知道系统保存了什么、为什么用于本次任务，以及怎样修改。

不要把所有随口表达都当稳定画像。测试临时要求、长期变化、不同项目及删除传播，确认系统既不遗忘必要信息，也不无差别永久保存。

### 8.7.5 多 Agent 协作系统

#### 多个 Agent 一致，怎样判断是不是独立依据

研究 Agent 从错误 Wiki 得到“一人审批”，执行 Agent 又读其摘要，审核 Agent 最后复述相同结论。表面上三者一致，底层却只有一个错误来源，并没有三次独立验证。

协作日志应记录每个主张依赖的来源及版本，而不只记录 Agent 名称。审核者可以回到批准规范或业务状态核对；若仍使用同一摘要，只能证明传播一致，不能提高事实可信度。

不同应用的验收重点因此不同：企业问答强调来源和权限，Coding Agent 强调工作区快照与实际验证，长任务强调副作用和恢复，个人助手强调更正与撤回。复用底座不意味着共用一套模糊成功指标。

场景报告先列不可接受失败，再比较一般任务效果。例如任务完成但泄露私有偏好，不应算可接受成功；输出正确步骤却未真正执行测试，也不能写为当前构建已通过。

每个应用建立损失函数前，先列不可接受失败。例如企业问答不能跨部门泄露，Coding Agent 不能把别的提交结果当当前测试，长任务不能重复副作用。然后再优化一般成功率。平均指标掩盖低频高代价错误时，按场景分层报告。

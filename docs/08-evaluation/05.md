# 8.5 系统工程指标

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。资料核验日期：2026-11-13。

## 要解决的问题

成本、性能和可靠性如何一起报告？

区分离线构建、在线查询与持续维护成本。使用固定数据与并发配置，记录冷启动、稳态和故障期间表现，避免只展示最好一次。

### 8.5.1 查询延迟与吞吐

#### “延迟变快”可能只是把失败排除了

假设方案 A 的 100 次请求中 99 次成功，1 次超时；方案 B 只有 90 次成功，10 次超时。如果只对成功请求排序，B 的 P95 可能更低，但更多用户没有得到结果。这是指标选择造成的表面改善，不能直接认定服务更快。

参考报告同时给成功延迟分布、超时和失败数量、整体目标达成率，并说明测量起止点是否含排队、重试和模型调用。超时请求可用预先定义的删失或服务目标口径处理，不能静默丢掉。

冷缓存、热缓存和持续更新应分别测。若 B 靠不刷新缓存变快，却返回旧规范，性能结果不满足正确性前提；若查询量很少，离线预处理成本又可能无法摊薄。

这些数字是解释统计偏差的假设样本，并非项目性能。真正结果需保存请求日志、配置与负载，按相同条件计算，不以一次开发机体验替代尾延迟或吞吐结论。

p95 应注明样本数、并发、超时和失败如何计入。若只统计成功请求延迟，最慢的超时请求被排除后会得到虚假的改善。分别报告成功分布、超时率和总体服务目标达成率。

### 8.5.2 Token 与推理成本

成本分形成、更新、检索、重排、生成、评分与运维记录。对同一时间窗口既报告绝对开销，也按实际查询量摊销，避免忽略预处理费用。

模型、供应方和计价日期明确保存；未调用外部服务时只记录可确认的调用计数，不填写假定账单。缓存命中和重试也纳入统计。

LlamaIndex 缓存命中会改变转换调用量，因此实验应分别报告冷启动、热缓存和来源变更三类负载。记录实际供应方、模型版本、请求量和统计日期；费用按当次账单或计价计算，未连接外部服务时只报告调用计数，不填货币成本。[R17][固定版本源码](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L58-L113)。

总成本可写为 Ctotal=Cbuild+Cupdate+Cquery+Cjudge+Coperations。对固定时间窗口按实际查询量摊销，并同时保留绝对成本；查询量极少时，预构建大型主题图谱可能不经济。

### 8.5.3 存储和索引维护成本

存储费用包括原文、版本历史、向量、图、摘要、日志和备份。更新与删除还会产生重建、碎片清理和临时双代际容量。

按对象类型与保留期估算，再用代表性变更量测量。只计算最新向量数量会严重低估治理与历史责任，压缩也不能绕过必须保留的证据。

### 8.5.4 可扩展性

扩展性测试同时增加读取、写入、依赖扇出和治理任务，观察积压是否持续增长。查询吞吐扩展了，但更新追不上，用户仍会越来越多读到旧结果。

记录资源、分区方式及瓶颈迁移。每次扩大规模保持相同正确性回归，不能通过减弱权限或版本检查获得看似更好的性能。

假设在线查询保持稳定，而每分钟新增的重建任务持续多于完成量，系统会累积索引落后。单次压测看不出问题，应持续记录任务年龄、待处理数量、删除传播及当前答案版本。扩展方案只有在持续负载下仍能追平并保持正确性，才支持该工作负载；增加查询节点并不能自动修复离线瓶颈。

### 8.5.5 可靠性与运维复杂度

可靠性包括供应方不可用、队列重投、构建失败和部分存储超时后的行为。需要定义降级、重试、补偿与恢复时间，并验证业务不变量。

运维复杂度也要计入：谁处理死信、怎样重放、如何确认删除完成。只有自动重试而没有次数、幂等和人工入口，可能把短暂失败变成持续重复写入。

# 2.1 信息的语义分类

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

信息应按什么维度分类？

语义类型回答内容在表达什么，不回答谁可访问或用哪种数据库。事件可包含实体、关系和事实；先拆出可验证断言，再保留事件级关联。

## 机制与细分考点

### 2.1.1 Fact：事实

Fact 是带条件、可被证据支持或反驳的陈述；未经验证的 Claim 不直接标为事实。审批要求必须附项目和生效时间。

### 2.1.2 Concept：概念

Concept 定义一类对象，需要范围、区分特征与反例。术语同名并不代表团队理解相同。

### 2.1.3 Entity：实体

Entity 是可持续识别的对象，名称只是可变属性。稳定 ID 应独立于显示名，重名对象不能按字符串合并。

### 2.1.4 Relation：关系

Relation 是带方向和条件的关联，需要两端实体、类型、时间与证据。文本共现不等于因果关系。

### 2.1.5 Rule：规则

Rule 包含前提、结论、约束和例外。紧急发布可能遵循特殊流程，只提取人数会丢失适用边界。

### 2.1.6 Event：事件

Event 记录参与者、时间、行动和结果。事件中有人提出某说法，不代表该说法已被验证。

### 2.1.7 Preference：偏好

Preference 是主体的倾向，需记录任务范围与明确程度。本次简短不能默认升级为永久偏好。

### 2.1.8 Experience：经验

Experience 将行动、环境和结果关联起来；成功经验脱离环境条件后，很容易变成错误建议。

### 2.1.9 Procedure：程序性知识

Procedure 是带前置条件、步骤、检查点及退出条件的方法。可执行流程与纯建议需要不同授权。

## 推导与工程过程

分类时同时保存原始表达与规范化断言。原文“这次可以先别走双人审批”至少包含说话者、一次性范围和可能的授权问题，不能直接提成“发布不需要双人审批”。规范化记录可写为主体 atlas、行为 ordinary_release、条件 current_request、陈述 candidate_exception，并标记尚未验证授权。

这里区分语义与治理尤其重要：一条 Preference 可以是公开测试数据，也可以是私有个人偏好；一条 Rule 可以是候选而非有效规则。语义类型无法代替访问和验证状态。

## Atlas 案例

发布失败包含事件、结果和原因候选。日志可以证明失败发生，原因解释还需额外证据。

## 适用条件与局限

分类允许多标签，不能强迫所有表达只属于一个桶。

## 阅读检查

指出案例的输入、输出、约束及失败点；若缺失证据、主体或有效时间，哪些判断不再成立？用本节机制解释原因。

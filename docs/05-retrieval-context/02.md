## 要解决的问题

RAG 的变化究竟改变了什么？

RAG 在生成前或生成过程中获取外部证据。原始 RAG 论文提供参数与非参数信息结合的一种研究形式，工程中常用的 RAG 是更广的流水线称呼。[R01]

### 5.2.1 RAG 的定义与工作机制

RAG 在回答前取得外部材料，再让生成模型据此组织答案。对审批问题，流程包括定位项目与时点、检索规范、核对证据条件、装配输入和生成引用。

检索失败与生成误用是两种错误。保存候选和最终上下文，才能判断该修复索引、选择策略还是回答约束；只保存最终答案无法归因。

### 5.2.2 Naive RAG

Naive RAG 常以固定切块、向量 Top-K 和直接拼接作为起点。它便于建立基线，但表格条件跨块、旧版更相似、镜像占位等问题都会影响结果。

先用少量有明确证据的题目观察每一步，再增加复杂模块。简单方案并非必然不足；当文档小、版本清楚、条件局部完整时，它可能已满足需求。

### 5.2.3 Advanced / Hybrid RAG

改进 RAG 应针对已观察到的失败。错误码漏召回可加关键词通道，相关但不回答问题的段落过多可加重排，条件分散则需要结构化分块或补充邻接文本。

每次只改变可解释因素，记录收益与额外延迟。不能把查询改写、重排、图和摘要全部叠加后，只凭答案变好就认定每个模块都有贡献。

### 5.2.4 Hierarchical RAG

层次检索先定位主题或文档，再进入详细段落。例如先找到发布流程章节，再找普通发布人数和角色限制。上层摘要用于导航，下层原文用于支持具体结论。

摘要可能漏掉例外，不能仅因上层未提到某条规则就判定不存在。保留回到原文的路径，必要时扩大候选范围，并分别评测导航和证据定位。

### 5.2.5 GraphRAG

GraphRAG 可借助实体和关系组织材料，例如先定位项目及依赖服务，再取相关说明。它适合关系驱动的问题，但抽取、实体合并和图更新都会增加误差与维护成本。

不要把任何使用图数据库的 RAG 都视为同一种实现。先说明图怎样构建、检索走哪些关系、答案依赖哪些原始证据，再与文本检索作对照。

例如问题是“数据库升级影响哪些服务以及各自的发布限制”。关系通道先取得受影响服务及路径，再按服务身份查询现行发布规范；图提供候选范围，文本证据提供具体限制。若实体消歧把同名服务合并，后续即使规范检索完全正确，也会回答另一个服务的要求。应分别观察图覆盖、实体对应和证据使用；这是一种参考组合，不代表所有 GraphRAG 项目的相同默认流程。

### 5.2.6 Agentic RAG

Agentic RAG 允许模型根据当前证据决定下一次检索。例如先找到人数要求，却缺少角色限制时，再查相关章节。与固定一次检索相比，它能追踪证据缺口，也可能重复查询或扩大成本。

应定义停止条件、调用预算和允许工具。模型提出下一步不等于查询已获授权；每次工具访问仍使用可信范围，并在证据不足时停止而非无限搜索。

### 5.2.7 检索召回、重排序与证据覆盖

#### 从一个不完整答案反推检索链哪里出了问题

用户问“普通发布需要几人，提交人能参与吗”。规范人数在正文 c1，角色禁止在表格 c2，紧急例外在 c3。系统只取回 c1 和 c3，回答“需要两人，提交人可以参与”，其中第二句没有证据支持。

先看原始候选：若 c2 从未出现，重排无法修复，需检查分块、查询表达、通道与 K；若 c2 已出现但被装配阶段丢掉，应修复选择与预算；若 c2 已进入最终输入却仍答错，应检查生成是否理解否定与角色。三种失败不能用同一个“提高召回数”解决。

这里可把证据需求明确列为人数、角色和例外适用性。c1 支持人数，c2 支持角色，c3 只用于说明不适用本题的紧急分支。候选数量更多不保证需求更完整，十份人数镜像也不能补出角色限制。

下一次检索可以围绕缺口查“提交人 审批资格”，而非无条件再搜整题；补到 c2 后重新核对是否为同一版本和范围。固定流程或 Agent 多轮流程都可以这样做，但停止条件应是必要证据与任务要求已核对，或者预算已用尽并明确报告不足。

LlamaIndex 的文档处理解决可检索节点的形成，不能保证每个业务问题的证据完整。实验应加入跨块条件、相似旧版与例外条款，比较固定 K 和按证据缺口补检索；没有运行前不宣称后一种一定更好。[固定版本源码](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L469-L507)。

排查 RAG 错误按顺序检查：金标准证据是否入库；是否被候选召回；是否被重排留下；是否进入最终上下文；答案是否正确引用。每一阶段保存对象 ID 与版本，便于做漏斗分析。只记录最终答案无法区分检索失败与生成失败。

Agentic 检索的停止条件可为已覆盖全部子问题、预算耗尽、连续调用无新增证据或需要人工澄清。若只有轮数上限而没有证据覆盖标准，系统可能早停；若只追求覆盖而没有预算，则可能陷入搜索循环。

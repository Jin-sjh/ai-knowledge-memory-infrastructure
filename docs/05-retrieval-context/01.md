# 5.1 信息访问基础

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。资料核验日期：2026-11-13。

## 要解决的问题

不同查询应该走哪条访问路径？

先识别查询意图与精确约束，再选择 SQL、全文、向量、图或直接阅读。检索技术是互补工具，所有路径都要经过相同可见性与时态约束。

### 5.1.1 精确查询与 SQL / API

问“u1 当前在 Atlas 的答复偏好是什么”，主体、范围和属性已明确，按键查询当前档案比语义搜索更直接。精确查询返回确定对象或不存在，不需要让新旧偏好在相似度上竞争。

同样，审批是否完成应查业务状态或受控 API。模型可解释返回结果，但不能用相关聊天代替当前执行事实。

官方 LangGraph 示例按 namespace/key 读取偏好，不需要 embedding；Store 的使用不等于向量搜索。实现联合访问时，可让精确档案和项目文档走不同路径，在候选已经完成授权后再合并。性能与正确率应分别测量。[R16][固定版本源码](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/store/memory.ts#L188-L219)。

### 5.1.2 关键词与全文检索

关键词检索适合精确名称、错误码、版本号和术语，例如搜索 ERR_ROLE_MISMATCH。它能保留字面匹配优势，却可能漏掉“审批者角色不符”这样的改写。

需要决定分词、字段和排序口径，保留命中位置供回查。不要因为文本包含错误码就认定故障原因相同，后续仍需比较环境与时间。

### 5.1.3 Embedding 与语义检索

语义检索帮助把“为什么部署被拦住”匹配到“审批条件未满足”，适合措辞不同的问题。生成查询向量后取相近文本，再将结果作为候选核对。

相关性不能替代状态和权限。旧规范可能更接近问题措辞，镜像文档也可能占据多条结果，因此先后还需版本过滤、重复控制与证据选择。

### 5.1.4 Hybrid Search

混合搜索先让不同通道各自查找候选，再合并结果。例如错误码可由关键词通道找到，措辞不同的故障描述可由语义通道补充。同一对象在两路都出现时，最终只占一个候选位置，但保留各路排名，便于解释。

两路的原始分数可能采用不同尺度，不能不经处理直接相加。一种办法是使用排名：名次越靠前，贡献越大。RRF（倒数排名融合）采用的一个形式是：

~~~text
融合分 = 各通道的 1 / (c + 该通道排名) 之和
~~~

这里排名从 1 开始；某通道没有返回该对象，就不贡献分数。c 是一个正的平滑参数，用来调节头部排名的影响，需要在开发集选择。下面取 c=60，仅用于手算说明。

| 候选 | 关键词排名 | 语义排名 | 计算 | 融合分约值 |
| --- | --- | --- | --- | --- |
| d1 | 1 | 20 | 1/61 + 1/80 | 0.02889 |
| d2 | 3 | 2 | 1/63 + 1/62 | 0.03200 |

d1 虽在关键词通道排第一，d2 在两路都较靠前，因此综合分更高。这个分数表达的是排名表现，不表示材料更真实、更新或更有权威。

若 d1 是现行规则、d2 是旧版，当前查询仍应排除 d2；历史查询则按目标时点另选版本。参考流程先按稳定身份合并候选和镜像观测，检查权限与适用状态，再对合格集合融合排序，最终读取时复查状态。不能靠给新版本加一点分来代替资格判断。

融合也不能找回所有通道都漏掉的证据。已知对象身份时可直接精确读取，不必调用全部通道。是否使用混合搜索，应由具体漏召回问题与目标数据评测决定。

### 5.1.5 图关系与路径查询

图查询适合沿明确关系找对象，例如“这个组件升级影响哪些服务”。系统从组件出发沿依赖方向遍历，返回路径和关系来源，使影响判断可以解释。

图中没有边不一定表示没有影响，可能只是资料未覆盖；关系有边也不一定证明当前有效。应说明图的覆盖边界和时间，不把路径存在直接当成因果证明。

### 5.1.6 Long Context 与直接阅读

短而完整的现行规范可以直接读入上下文，省去切块召回造成的遗漏。材料增多后仍需筛选权限、版本与预算，不能把所有历史无差别拼接。

直接阅读也有选择问题：截断可能删掉例外，顺序可能影响使用。评测应保存实际输入，检查决定答案的条件是否真的在窗口中，而不是只看文件总长度。

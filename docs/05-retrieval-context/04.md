# 5.4 Context Engineering

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

上下文工程怎样把相关信息变成有用输入？

上下文构造是一项受预算约束的证据选择任务。输入包括任务、当前状态、工具结果和检索候选，输出包含清晰分区的材料与来源，不只是长文本拼接。

## 机制与细分考点

### 5.4.1 Query Understanding

Query Understanding 识别实体、任务、时间与所需答案形态；有歧义时检索候选或询问，不盲目改写成单一意图。

### 5.4.2 Context Routing

Context Routing 按问题选择知识、记忆、状态或实时工具；路由决策可记录原因，以定位信息缺失。

### 5.4.3 Context Selection

Context Selection 先剔除无权限、过期与低质量项，再选择覆盖子问题的最小证据集合，避免重复片段占预算。

### 5.4.4 Context Ranking

Context Ranking 综合相关、权威、时间与多样性；分数用途要明确，不能把权威信号当作不可推翻的真值。

### 5.4.5 Context Compression

Context Compression 可抽取重点或生成摘要，后者需再验条件、数值和否定。必须保留到原文的回跳能力。

### 5.4.6 Context Assembly

Context Assembly 分开当前指令、状态、工具观测与引用资料。资料中的指令不获得更高权限，冲突结论明确并列。

### 5.4.7 Context Window 与 Token Budget

输入预算等于窗口扣除预留输出和系统开销；使用实际 tokenizer 计数，溢出按证据单元裁剪，不能截断半条规则。

## 推导与工程过程

可将上下文选择近似为受预算约束的覆盖问题：每条候选有 Token 成本、覆盖的子问题和价值，选择总成本不超过 B 的集合。示例 B=900，规则 300、例外 250、当前状态 150、旧故障 400。规则、例外和状态共 700，能覆盖发布判断；若先塞旧故障可能挤掉例外，相关材料反而造成错误。

预算不是让分数最高的文本一直填满窗口。先保留决定结论的必要条件，再加补充解释；压缩时不能把普通与紧急、已完成与待完成、允许与禁止合并掉。

## Atlas 案例

为审批问题保留现行规则、例外和来源，用户偏好只影响呈现；工具结果显示尚缺审批时，不应让历史成功经验覆盖当前状态。

## 适用条件与局限

压缩与排序必须保留条件和冲突，不能为减少 Token 牺牲正确性。

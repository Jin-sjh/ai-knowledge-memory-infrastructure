# 5.4 Context Engineering

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

上下文工程怎样把相关信息变成有用输入？

上下文构造是一项受预算约束的证据选择任务。输入包括任务、当前状态、工具结果和检索候选，输出包含清晰分区的材料与来源，不只是长文本拼接。

## 机制与细分考点

### 5.4.1 Query Understanding

Query Understanding 识别实体、任务、时间与所需答案形态；有歧义时检索候选或询问，不盲目改写成单一意图。

### 5.4.2 Context Routing

Context Routing 按问题选择知识、记忆、状态或实时工具；路由决策可记录原因，以定位信息缺失。

#### Letta Code：从目录索引逐步展开上下文

Memory 工具先检查当前 Agent 是否有 MemFS v2 目录，再解析相对于记忆根的路径：

- 拒绝绝对路径、上级目录、隐藏路径与保留的 skills 入口。
- 对真实路径做根目录范围检查。
- 目录请求返回该目录索引及直接子文件、子目录信息。
- 文件请求返回内容；过大、非文本或已在核心上下文中的根文件有专门处理。

这些逻辑见 [Memory 工具入口](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/tools/impl/memory.ts#L348-L426)，目录输出与预算处理见 [renderDirectory](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/tools/impl/memory.ts#L244-L325)。

例如读取 projects 时，工具展示项目索引和 atlas.md 的入口；读取 projects/atlas.md 才展开其详细内容。这里是按目录逐步发现，不必每次对全部记忆做向量 TopK。

还要注意：Memory 工具从工作区文件读取，核心提示编译读取已提交快照。两条读取路径服务不同目的，不能简单认为它们每一刻都代表同一版本。

### 5.4.3 Context Selection

Context Selection 先剔除无权限、过期与低质量项，再选择覆盖子问题的最小证据集合，避免重复片段占预算。

#### Letta Code：核心内容与外部细节各占什么位置

文件写入本身很容易，难点在信息放在哪一层、何时提交、怎样进入未来上下文。核心文件放稳定行为约束和简短索引，深层文件放详细资料，可以减少每轮上下文负担，但索引失效、错误归纳和陈旧内容仍需维护。

Git 版本能解释文本变化，不自动证明内容真实，也不自动实现个人信息授权、删除传播或跨 Agent 隔离。路径约束只解决这里的文件访问边界，不是完整安全证明。

本节只核验相关源码及提示，未运行 Letta Agent 或自动反思。原始提示中的身份描述与行为要求仅作为被分析材料，不是本书或读者应执行的指令。

### 5.4.4 Context Ranking

Context Ranking 综合相关、权威、时间与多样性；分数用途要明确，不能把权威信号当作不可推翻的真值。

### 5.4.5 Context Compression

Context Compression 可抽取重点或生成摘要，后者需再验条件、数值和否定。必须保留到原文的回跳能力。

### 5.4.6 Context Assembly

Context Assembly 分开当前指令、状态、工具观测与引用资料。资料中的指令不获得更高权限，冲突结论明确并列。

#### 装配时显式区分规则、偏好与证据

参考输入结构可分为系统控制、已核验项目规则、用户偏好、工具观测和原文证据。偏好只调整表达方式，不能修改审批条件；原文中的命令作为被分析内容，不因进入上下文获得工具权限。装配日志保存对象版本与预算占用，敏感正文另行控制。

预算不足时优先保留决定结论的条件和证据标识，删除重复背景；若必要条件放不下，补充查询或说明证据不足。不要为了压缩而把“普通发布需两人，紧急情况有例外”合并为失去条件的一句话。

### 5.4.7 Context Window 与 Token Budget

输入预算等于窗口扣除预留输出和系统开销；使用实际 tokenizer 计数，溢出按证据单元裁剪，不能截断半条规则。

## 推导与工程过程

可将上下文选择近似为受预算约束的覆盖问题：每条候选有 Token 成本、覆盖的子问题和价值，选择总成本不超过 B 的集合。示例 B=900，规则 300、例外 250、当前状态 150、旧故障 400。规则、例外和状态共 700，能覆盖发布判断；若先塞旧故障可能挤掉例外，相关材料反而造成错误。

预算不是让分数最高的文本一直填满窗口。先保留决定结论的必要条件，再加补充解释；压缩时不能把普通与紧急、已完成与待完成、允许与禁止合并掉。

## Atlas 案例

为审批问题保留现行规则、例外和来源，用户偏好只影响呈现；工具结果显示尚缺审批时，不应让历史成功经验覆盖当前状态。

## 适用条件与局限

压缩与排序必须保留条件和冲突，不能为减少 Token 牺牲正确性。

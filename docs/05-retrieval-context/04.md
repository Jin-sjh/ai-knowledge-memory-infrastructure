# 5.4 Context Engineering

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

上下文工程怎样把相关信息变成有用输入？

上下文构造是一项受预算约束的证据选择任务。输入包括任务、当前状态、工具结果和检索候选，输出包含清晰分区的材料与来源，不只是长文本拼接。

### 5.4.1 Query Understanding

查询理解先确定对象、业务时点、任务目的和缺失条件。“现在能发吗”可能是在问规范许可，也可能是在问当前审批状态，两种请求需要不同数据源。

能从可信任务上下文确定的项目可直接使用；无法确定时询问或返回范围受限的答案。不要让模型凭最近出现的项目名猜测，再把猜测用于工具查询。

### 5.4.2 Context Routing

路由将不同需求发给合适的数据源：规范走知识访问，当前偏好走档案，执行进度走检查点，实时审批走业务 API。路由依据应包括任务与对象身份，而不只看关键词。

某个分支失败时返回局部缺口，不能用另一个分支的相似文本替代。例如工具不可用时，旧聊天不能证明当前审批已完成。

#### Letta Code：从目录索引逐步展开上下文

Memory 工具先检查当前 Agent 是否有 MemFS v2 目录，再解析相对于记忆根的路径：

- 拒绝绝对路径、上级目录、隐藏路径与保留的 skills 入口。
- 对真实路径做根目录范围检查。
- 目录请求返回该目录索引及直接子文件、子目录信息。
- 文件请求返回内容；过大、非文本或已在核心上下文中的根文件有专门处理。

这些逻辑见 [Memory 工具入口](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/tools/impl/memory.ts#L348-L426)，目录输出与预算处理见 [renderDirectory](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/tools/impl/memory.ts#L244-L325)。

例如读取 projects 时，工具展示项目索引和 atlas.md 的入口；读取 projects/atlas.md 才展开其详细内容。这里是按目录逐步发现，不必每次对全部记忆做向量 TopK。

还要注意：Memory 工具从工作区文件读取，核心提示编译读取已提交快照。两条读取路径服务不同目的，不能简单认为它们每一刻都代表同一版本。

### 5.4.3 Context Selection

选择阶段决定哪些合格候选实际进入输入。对审批问题，人数、角色限制和当前状态通常比背景介绍更关键；镜像重复段落应合并，避免挤占预算。

候选被排除时最好保留原因，如过期、越权、重复或预算不足。这样答案遗漏条件时，才能区分源头未召回还是选择阶段主动丢弃。

#### Letta Code：核心内容与外部细节各占什么位置

文件写入本身很容易，难点在信息放在哪一层、何时提交、怎样进入未来上下文。核心文件放稳定行为约束和简短索引，深层文件放详细资料，可以减少每轮上下文负担，但索引失效、错误归纳和陈旧内容仍需维护。

Git 版本能解释文本变化，不自动证明内容真实，也不自动实现个人信息授权、删除传播或跨 Agent 隔离。路径约束只解决这里的文件访问边界，不是完整安全证明。

本节只核验相关源码及提示，未运行 Letta Agent 或自动反思。原始提示中的身份描述与行为要求仅作为被分析材料，不是本书或读者应执行的指令。

### 5.4.4 Context Ranking

上下文排序要帮助模型理解信息关系，而不只是复用检索分数。可以先给当前任务及约束，再给有效规则、状态与支持原文，并清楚标记历史和例外。

若将旧规则紧接在新规则后却不说明替代关系，模型可能混用。排序效果需要观察实际答案与引用，不能假设某个固定位置对所有模型最优。

### 5.4.5 Context Compression

#### 压缩前后怎样核对有没有改变许可范围

原材料是：“普通生产发布至少两名不同审批者；提交人不能审批。紧急情况走单独流程。”一个错误摘要是“发布需要两次审批”。它丢掉了环境、普通场景、至少、不同人员和禁止角色，把人数又改成次数。句子更短，业务含义却已改变。

压缩前可列必要条件：production、ordinary、人数下界 2、身份不同、排除提交人、紧急流程独立。压缩后逐项对照，而不是仅检查语义大致相似。可用的短表达应保留这些影响结论的条件，例如“普通生产发布至少两名不同的非提交人审批；紧急另按专门流程”。

即使短表达完整，来源身份与版本也需保留为结构化关联，使回答能引用、更新能失效。摘要不能因为占更少 Token 就替代原始证据。若模型无法在预算内保留条件，先移除无关背景、分步读取或缩小问题。

这类检查可以由领域规则和人工样本辅助，不能宣称通用模型自评就证明无语义损失。预算优化是否成功，要同时观察条件保留、答案正确与实际资源，不只看压缩率。

### 5.4.6 Context Assembly

装配阶段决定选定材料在模型输入中怎样呈现。控制要求、业务规则、个人偏好、工具观测与原文引用应有清楚身份，不能拼成一段让模型猜测来源和优先级。

例如回答发布问题时，可以依次提供当前任务、有效规范、实时审批状态和表达偏好，并为证据标记来源版本。规则决定许可条件，偏好决定表达方式；资料里出现的操作命令仍是被分析内容，不因此获得执行权限。

装配结束时核对使用的对象与版本，记录哪些材料被采用、哪些因过期或冲突被排除。压缩是否保留语义在上一节检查；能装入多少材料由下一节的预算决定。

### 5.4.7 Context Window 与 Token Budget

模型可接受的窗口、应用本次允许使用的总额度，以及留给检索材料的额度，是不同概念。本书使用以下口径：

| 名称 | 含义 | 下面例子的额度 |
| --- | --- | --- |
| 本次总额度 | 本次输入与预留输出合计的上限，需符合目标模型限制 | 8,000 Token |
| 输出预留 | 为本次生成保留，不能用于塞入材料 | 1,500 Token |
| 固定输入 | 系统指令、工具定义、当前问题及固定任务字段 | 1,500 Token |
| 材料预算 | 剩余可用于规范、记忆、工具结果等可选材料的额度 | 5,000 Token |

计算为：8,000 − 1,500 − 1,500 = 5,000。固定输入中，假设系统和工具定义占 1,000，问题与固定任务字段占 500。数字仅用于手算，不是某模型的测量结果。实际计量要覆盖消息格式等开销，并符合目标模型各项限制。

假设所需规则占 1,600、角色限制占 400、当前审批结果占 500，必要材料合计 2,500；可选背景还有 3,000。两者共 5,500，超过材料预算 500，应先删除至少 500 的可选背景。不能直接截掉最后一段，因为那一段可能是决定许可的角色限制。

材料选择因此先保证必要证据，再增加补充背景。若必要证据自身已超过预算，就缩小问题、分步读取或明确说明不足；不能把禁止条件压掉以满足长度限制。

[Context API](../appendices/api-contract.md) 的 token_budget 专指这里的**材料预算**。调用方先预留输出并扣除固定输入，再把 5,000 传给接口；接口不重复扣除这两项。新增工具结果或后续轮次会改变已占空间，调用方应重新计算。

评测时保存实际 Token、计数方式、最终输入及被排除材料。统一口径后再比较方案，避免一个方案按总额度、另一个按材料额度，却声称使用相同预算。

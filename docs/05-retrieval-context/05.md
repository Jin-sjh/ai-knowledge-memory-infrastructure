# 5.5 知识与记忆联合访问

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

知识、记忆和状态如何联合访问？

查询规划分解所需信息，多源检索后统一做授权、有效性、冲突与证据充分性检查。最终回答说明结论适用的主体与时间，不将多源文本扁平拼接。

## 机制与细分考点

### 5.5.1 多源检索与查询规划

多源规划列出子问题与来源，限制分支和调用预算。先执行能淘汰分支的精确查询，可减少无用语义检索。

### 5.5.2 Knowledge + Memory Retrieval

Knowledge 与 Memory 可以并行检索，但保留类型标签；个人偏好不应改写组织规则，规则也不能自动代表用户意愿。

#### 联合访问的一次完整决策

对“现在能否发布，简短回答”，先精确读取任务状态和有效偏好，再检索当前项目规则。规则决定可否发布，状态说明审批是否完成，偏好决定先给结论。任一数据源缺失都要局部标明，不能拿用户的历史习惯替代审批事实。

本书建议返回带用途的候选：policy、preference、execution_state，并保留各自来源与版本。合并阶段检查时间和权限，装配阶段才决定长度。LangGraph 的独立 Store 与检查点示例可验证两路数据的分工，但它没有实现本节完整联合检索服务。 [固定版本源码](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/store/memory.ts#L188-L219)。

可以把这次查询展开为以下参考访问计划，所有分支在可信身份约束下执行。

| 分支 | 输入 | 需要的输出 | 缺失时的处理 |
| --- | --- | --- | --- |
| 项目规则 | project_id、业务时点 | 有效规则及证据 | 不判断是否允许发布 |
| 用户偏好 | user_id、project_id | 当前有效表达偏好 | 使用产品默认表达 |
| 任务状态 | run_id、checkpoint 版本 | 审批完成情况 | 先核对业务状态 |
| 装配 | 三路授权结果 | 结论依据与表达约束 | 显式列出未确认项 |

三路都返回不代表一定能回答。规则要求两人审批，而状态只有“一人已审批”时，应明确指出条件未满足；偏好要求简短也不能删除这个决定性理由。

### 5.5.3 State / Tool / Knowledge 联合上下文

State 表示执行位置，Tool 提供当前观测，Knowledge 提供约束。三者冲突时核对时间和来源，不能按拼接顺序盲选。

### 5.5.4 来源与权限过滤

授权在召回约束、主记录回查和最终输出前检查。异步旧索引不得成为绕过撤权的路径，缓存也带权限版本。

### 5.5.5 冲突信息与过期信息处理

对过期记录区分历史引用与当前使用，对冲突记录保留双方及原因；未经裁决不能输出单一确定行动。

### 5.5.6 拒答、证据不足与不确定性

证据不足时拒绝作确定判断，说明已知、未知和补充材料。拒答准确率与可回答问题误拒率应分别统计。

## 推导与工程过程

联合回答可保留三列表：规则约束、当前观测、用户呈现偏好。发布是否满足由前两者比较决定，第三者只决定表达。若当前观测不存在，系统可给条件式结论“若只有一人则未满足”，而不能把用户问句直接当作已经核验的工具事实。

最终输出门检查每个引用对象的当前权限和删除状态，避免构造期间发生撤权后的竞态。若权限已变，丢弃受影响上下文并重新组装，而不是仅移除引用标签却保留泄露文本。

## Atlas 案例

u1 问发布准备好了没有：工具读取当前审批状态，知识提供门槛，记忆决定先给结论；缺审批时回答未就绪并引用规则。

## 适用条件与局限

无证据时可以解释缺什么并提出下一步，不应仅靠语气掩盖不确定性。

# 4.6 生命周期治理

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

治理怎样覆盖所有副本？

以版本账本、访问审计和删除任务组织治理。先阻断在线访问，再清理索引和派生物；各存储确认前不能宣称完成。

### 4.6.1 版本控制与历史记录

内容修订生成新版本，保留修改者、依据及时间，使旧答案仍能回溯。当前指针可变化，但证据引用应指向具体版本，不能随 latest 自动漂移。

普通数据库历史便于追踪，不自动具备防篡改能力。若要求强审计，需要独立日志、访问控制和保留措施；不要仅因有 version 字段就宣称满足合规审计。

### 4.6.2 审计与可追溯性

审计要能重建一次决策：谁以什么身份查询，系统选了哪个来源版本，哪些对象被过滤，最终使用了什么规则。只记录“成功”无法解释错误从何而来。

敏感正文不应无差别写入普通日志。可以保存受控引用与配置哈希，在授权范围内回查；审计记录自身也要有权限、保留期和删除责任。

### 4.6.3 权限变更与数据删除传播

用户退出项目后，主库、向量索引、图路径、摘要和上下文缓存都可能残留相关内容。权限变更应先影响在线访问，再异步处理副本，不能要求用户等待所有重建完成才生效。

删除任务为每种副本记录待处理、成功和失败，并支持幂等重试。对于无法追踪来源的摘要，系统难以确认是否已清干净，这正是派生依赖必须在生成时登记的原因。

Git 提交快照能提供可回溯版本，但当前文件删除不等于历史提交消失。若采用 Letta Code 类文件记忆，敏感内容的删除要求必须覆盖仓库历史与其他副本；本书并未据此证明其现成工具已实现完整删除传播。[固定版本源码](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L65-L198)。

删除协议的两个时间点分别是 Tblock 和 Tpurge。Tblock 表示任何在线入口已不能返回该信息，Tpurge 表示约定存储清理确认。两者之间允许内部受控清理，但不能在用户界面混成一个已删除状态。备份保留还需单列说明。

恢复演练应从旧备份启动隔离环境，先加载当前删除与撤权账本，再开放读取。若先开放服务后重放账本，即使最后清理正确，也存在信息重新暴露窗口。这是单测删除接口无法发现的问题。

#### 删除任务为何需要逐项确认

假设 u1 要求删除 Atlas 答复偏好，项目规范仍需保留。以下是参考任务清单。

| 对象 | 先阻断使用 | 完成清理的依据 |
| --- | --- | --- |
| 偏好主记录 | 标为删除，不参与当前行为 | 按策略清除或转为受控墓碑 |
| 向量条目 | 命中后回查当前删除状态 | 按稳定身份删除后核对 |
| 用户摘要 | 标记失效，不再装配 | 重建后不含该偏好 |
| 上下文缓存 | 旧版本键不再命中 | 按策略移除旧内容 |
| 项目规范 | 保持原有资格 | 回归确认没有误删 |

若向量服务超时，在线阻断仍可先成立，任务则保持清理未完成。告知用户的完成范围必须与确认结果一致，等待超时也不能把失败副本自动记为成功。

### 4.6.4 一致性校验与回滚

回滚不能只把当前内容指针切回旧版。例如旧版仍包含已撤权资料，直接回退索引会恢复不应可见的内容。回滚前核对内容、权限和依赖是否仍有效。

可以恢复业务内容版本，同时保留最新权限及删除状态。恢复后执行主库与派生物一致性检查，确认当前回答不再混用不同代际；备份可读取并不等于可以安全上线。

### 4.6.5 数据保留策略

不同对象需要不同保留策略：任务草稿可短期清理，审核证据可能需要更久，用户偏好则受撤回和用途限制。应说明保存目的、期限、例外和到期动作。

策略也要覆盖派生摘要、导出与备份。只在主记录上设置 TTL，不能保证相关副本同步消失；到期治理需要可枚举依赖和完成确认，而不是依赖所有组件恰好同时过期。

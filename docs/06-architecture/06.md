# 6.6 多租户与 Agent 集成

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

多租户与 Agent 运行时如何集成？

将身份、作用域与运行 ID 贯穿接口和存储。共享通过显式策略建立，不能依靠同一模型、同一向量空间或同一 Agent 名称推断可见性。

## 机制与细分考点

### 6.6.1 User / Project / Organization Scope

User、Project、Organization Scope 由可信授权上下文约束；项目归属变化后重新检查对象权限，不能仅相信旧标签。

### 6.6.2 多 Agent 共享知识

多 Agent 共享知识需要共同授权域和版本约定，Agent 写入的总结仍经过普通候选验证流程。

#### 共享知识与私有状态的联合边界

两个 Agent 可以读同一项目规范，但各自任务游标属于不同 thread，个人偏好又属于不同 user。参考授权上下文显式包含这三个标识，服务端核对用户是否属于项目，然后派生查询范围；不能由客户端提交任意 namespace 来证明权限。

若 Agent A 生成了项目总结，提升为共享知识前要重新检查输入依赖。只要总结引用了私有偏好，就不能因输出放在共享目录而自动公开。LangGraph 示例中的宽前缀查询用于说明存储组织与应用授权的区别，不能替代生产权限测试。 [固定版本源码](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/store/memory.ts#L188-L219)。

### 6.6.3 独立记忆与共享记忆

独立记忆与共享记忆通过策略区分；把个人经验提升为团队知识需去除不必要个人信息并重新审核。

### 6.6.4 Agent Runtime 与 Workflow

Runtime/Workflow 调用知识与记忆接口，运行步骤和工具执行保留在运行模块；控制指令与来源文本严格分区。

### 6.6.5 任务状态持久化与恢复

任务恢复读取检查点和副作用账本，先核对目标状态再继续。若远端操作已成功但本地未确认，不能直接重复执行。

#### LangGraph：检查点和跨会话 Store 的实际分工

本例直接导入官方 @langchain/langgraph 1.7.4，锁定依赖 @langchain/langgraph-checkpoint 1.2.2。使用 InMemoryStore、MemorySaver 和 StateGraph，未替换为本书模拟实现，也不需要模型、embedding 或 API Key。

Store 对 namespace/key 保存应用信息；MemorySaver 对 thread_id 等标识保存图状态。二者都在内存里，“可跨会话访问”不等于“进程退出后仍持久化”。

运行：

~~~sh
npm ci
npm run example:langgraph
npm run test:projects
~~~

[完整代码](../../examples/projects/langgraph-store.mjs)由确定性节点读取偏好，并用 reducer 累加 visits。观测结果如下，原始 JSON 见[运行记录](../../examples/projects/langgraph-recorded.json)。

| 调用顺序 | 会话 | 用户 | 节点读到的偏好 | 本会话 visits |
| --- | --- | --- | --- | --- |
| 1 | conversation-a | u1 | 详细解释 | 1 |
| 2：更新 Store 后 | conversation-b | u1 | 先给简短结论 | 1 |
| 3：继续原会话 | conversation-a | u1 | 先给简短结论 | 2 |
| 4 | conversation-c | u2 | 未设置 | 1 |

第二次调用表明，新会话可读共享 Store 中 u1 的当前偏好。第三次表明，原会话恢复自己的 visits，但读取的偏好仍来自当前 Store。**会话状态不是用户记忆的另一份自动同步副本。**

节点没有生成自然语言答案；表中的结果是代码读取的值，不是 LLM 遵循偏好的效果成绩。

MemorySaver.put 读取 thread_id、checkpoint_ns 和 checkpoint.id，将序列化检查点及父关系保存在对应会话下；缺 thread_id 会报错。[检查点写入](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/memory.ts#L462-L509)

因此不同 thread 可有独立执行状态，却共享同一个应用 Store。当前示例用真实 graph.getState 回查，conversation-a 的 visits 为 2，conversation-b 为 1，两个状态没有混在一起。

保存图状态不保证任意外部动作都不会重复执行。调用外部工具仍需幂等、确认与恢复设计，不能把检查点能力推广为所有副作用的 exactly-once。

### 6.6.6 权限隔离、安全与审计

服务层过滤配合数据库约束与审计；跨租户测试需覆盖索引、缓存、摘要和错误信息，防止旁路泄露。

#### LangGraph：原始 Store 接口仍需应用授权

示例最初按 u2 的 namespace 读取，得到未设置；随后给 u2 独立写入一条偏好，再直接调用原始 Store 的 search(["users"])，会同时得到 u1 和 u2 的记录。

这不是越权漏洞证明，而是说明原始 Store 是数据原语：更宽的合法查询前缀允许返回更多记录。应用必须根据认证主体限制可用 namespace，不能把 user_id 原样交给客户端自由决定。

本例的两个测试分别检查会话/Store 分工和宽前缀行为，没有宣称实现生产认证系统。

## 推导与工程过程

多租户隔离检查的最小闭包包含主库行、向量元数据、图路径、缓存键、摘要依赖、导出文件和错误消息。即使主库 RLS 正确，若上下文缓存只按 query 缓存，两个用户相同问题仍可能共享私有结果。[R08]

共享派生物不直接拥有比输入更宽的权限。最保守策略是要求读取者可访问全部依赖；若要生成不同权限视图，需要重新构建并证明输出不含隐藏依赖信息，不能只删掉来源标签。

## Atlas 案例

u1 允许使用个人偏好，但 u2 的回答不能召回该偏好。两个 Agent 可共享项目手册，却分别拥有私有任务状态。

## 适用条件与局限

数据库行级安全可作为纵深防护，仍需检查服务角色、表所有者与绕过权限。[R08]

# 6.5 模块通信与接口设计

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

接口如何表达版本与部分失败？

采用版本化 JSON 参考契约，身份由认证层注入，客户端请求不能自行声明跨租户权限。写入返回主记录版本，异步任务返回独立状态。

### 6.5.1 数据读写接口

写入接口应接收对象身份、来源版本、预期版本和幂等标识，并说明返回的是已接收、已提交还是已发布。读取接口则区分当前视图与指定版本。

例如提交成功但索引待更新，可以按 ID 读取，却未必立即语义检索到。让状态显式可见，调用方才能安排重试与用户反馈。

### 6.5.2 Search / Retrieve API

Search 适合返回按条件得到的候选及排序信息，Retrieve 可取得确定对象与证据。二者都应接受可信范围和业务时点，返回版本及排除状态。

不能只返回一段无身份文本，否则后续无法审核来源、删除依赖或解释引用。查询参数的 limit 也要区分候选量和最终上下文量。

### 6.5.3 Memory API

Memory API 应区分观察事件、确认偏好、查询当前值和请求删除。通用 add 接口无法独自表达临时指令与长期更正的差别。

参考响应返回采取的动作、相关对象和未决条件。若模型未提取内容、解析失败或存储不可用，应分别报告；空列表不能承担所有错误语义。

### 6.5.4 Context API

Context API 接收任务、身份、时点与预算，返回实际选用对象、必要文本和缺口说明。应用可以据此生成回答，也能解释为什么没有使用某段记忆。

接口不应默默扩张权限或把不可用数据包装成空上下文。输出预算不足以容纳必要条件时，明确要求补查或缩小问题，而非无提示地截断。

### 6.5.5 事件驱动更新与异步任务

异步事件让提取、索引和治理不阻塞所有请求，但引入延迟、重复和乱序。消费者按事件身份去重，按对象版本防止回退，并记录失败与重放位置。

例如来源 v2 的索引任务失败时，后台可重试同一目标版本；不要重新生成无关来源身份。在线读取要知道索引是否追平，不能假装最终一致意味着随时一致。

异步 API 的受理结果与完成结果分开建模。写主记录成功可返回对象版本与 indexing_job_id；客户端看到 201 只能确信主记录已提交，不能假设向量搜索立刻可见。删除接口则要求在线屏障先建立，再返回 202，后续任务负责清理。

错误契约应让调用方能作正确选择：409 先读新版本，429 按退避重试，证据不足补充来源，权限不可见不能通过换检索路径绕过。把所有失败都映射成“再试一次”会制造重复副作用。

### 6.5.6 Schema、错误处理和版本契约

#### 调用者收到同样的超时，可能面对不同事实

一次请求可能未到服务端，也可能主记录已提交但响应丢失，还可能主记录成功、索引未完成。客户端仅凭网络超时无法区分，所以重试协议需要请求身份和可查询状态。

首次请求以 request r42 提交候选 c3。再次使用 r42 时，服务端可以返回已有提交结果，而不是重新生成对象；如果客户端修改了请求内容，却复用同一幂等标识，应拒绝或明确视为另一操作，不能悄悄覆盖原意图。

业务对象的 expected_version 又承担另一责任：r42 尚未提交时对象若已被其他人改为 v4，则需报告前提过期。更换 request_id 不能绕过版本检查，修改 expected_version 也不能替代重新理解最新内容。

错误响应应解释下一步：未知提交先查状态，版本冲突重新读取与合并，限流按约定退避，权限不足停止访问。接口稳定不只是字段未变，更是这些恢复语义不会随版本升级悄悄变化。

Mem0 所读实现对模型调用异常和解析为空采用不同处理路径。适配公共 API 时应保留这种差异：供应方不可用可以重试，候选确实为空可以正常结束，解析失败则需要诊断。将三者都转换成空数组会隐藏质量问题。[固定版本源码](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L918-L1098)。

#### 一次异步写入的参考契约

以下字段是用于解释职责的接口草案，不是已上线 API。实际结构仍以[API 契约](../appendices/api-contract.md)为入口。

| 字段 | 示例 | 含义 |
| --- | --- | --- |
| request_id | req-42 | 跟踪请求，不等同对象身份 |
| candidate_id | pref-u1-atlas-3 | 稳定识别本次候选 |
| expected_version | 2 | 并发前提，过期时返回冲突 |
| persisted_version | 3 | 主记录已提交的版本 |
| index_state | pending | 检索索引尚未追平 |
| retryable | false | 是否允许原请求安全重试 |

若主库已提交而索引超时，应返回已提交版本及待索引状态；调用者可以按 ID 读取，后台重试索引。若返回笼统失败，客户端可能再次提取并生成新候选，导致重复。请求级幂等与候选级身份需要同时设计。

# 6.4 系统核心数据流

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

核心数据流在哪些点交接？

将写入与访问分为独立流水线，用版本化事件连接演进任务。每个阶段显式说明输入、输出、失败状态与可重试条件。

### 6.4.1 Knowledge Ingestion Pipeline

知识写入从来源快照开始，经过解析、分块、候选提取与验证，再发布为可访问对象。每个阶段保存输入版本与输出身份，失败后从已确认边界继续。

来源入库成功不等于知识可用；发布应检查规则条件与证据。异步索引未完成时，明确哪些读取方式已可用，避免调用端立即搜索却把空结果当成无知识。

### 6.4.2 Memory Formation Pipeline

记忆形成先识别表达者、任务范围及保存价值，再生成偏好或经历候选。临时要求与长期更正进入不同策略，保存后更新当前视图或读取裁决规则。

结果应能解释本轮为何写入或跳过。让所有聊天都自动提为长期记忆，既增加噪声，也使用户难以理解系统未来会如何使用。

### 6.4.3 Unified Retrieval Pipeline

联合检索先产生受授权的多路候选，再去重、核对时间与冲突，最后交给上下文选择。不同通道的分数不能直接等同，精确当前值也不必与经历竞争。

保留各通道贡献与淘汰原因，出现错误时才能知道缺失发生在哪一阶段。请求中某一路失败，应按任务重要性决定降级还是停止。

### 6.4.4 Context Construction Pipeline

上下文构建将任务、控制约束、有效知识、偏好和工具观测装配为明确结构。先保留决定结论的条件，再在预算内加入背景，并为回答预留输出空间。

装配完成后核对版本与权限，避免处理过程中来源已撤回。记录对象标识和配置可以帮助复现，敏感正文则采用受控存储。

### 6.4.5 Knowledge / Memory Evolution Pipeline

更新或删除事件到达后，先改变在线可见状态，再定位依赖并重建或清理。事件包含稳定标识与目标版本，使重复投递不重复产生业务对象。

若 v3 已生效，迟到的 v2 重建不能覆盖它。发布前重新核对输入代际；失败保留进度并重试，不把跨模块部分成功伪装成原子完成。

Mem0 的批量插入及失败回退表明底层写入可能部分成功。跨模块编排应记录每项对象的结果，并以补偿或重试恢复；不能把函数返回当作来源、历史、索引和实体关联全部原子提交的证明。[固定版本源码](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L918-L1098)。

一条更正事件应包含被更正逻辑对象、新内容版本和明确的原因，不携带对整个存储的任意执行指令。消费者只处理其负责的派生物，幂等检查当前状态。由此即使消息重复或乱序，也不会让旧派生任务覆盖更正。

读取路径不要等待所有异步任务无限完成。可返回主记录证据、降级为精确查询或清楚说明暂缺某视图；降级也必须执行同样的授权、有效期和冲突约束。

#### 主记录成功、索引失败时谁来继续

更正请求已将偏好提交为 v3，随后向量更新超时。参考处理保留主记录 v3，并给索引任务登记目标版本与未确认结果。当前档案可返回 v3，语义通道标明未追平并排除旧版默认用途。

后台按同一目标身份重试。若 v4 已出现，v3 的迟到结果不能恢复为当前视图。不能报告成整条请求什么也没发生，再重新提取生成另一个对象；每个模块需暴露真实提交边界，调用方才知道该查询、等待还是重试。

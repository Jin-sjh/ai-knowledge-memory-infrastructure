# 6.2 系统逻辑分层

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

五层分别承担什么责任？

分层按照语义责任划分：应用表达任务，上下文访问组织输入，知识与记忆服务管理策略，表示层定义实体，存储索引层实现持久化和访问加速。

### 6.2.1 Application / Agent Layer

应用层接收任务、选择工具并管理交互，例如“分析发布状态后给简短建议”。它提交主体和任务范围，不应自己从任意向量集合拼私有数据。

公共访问与治理规则下沉后，不同 Agent 能使用相同契约。应用仍负责动作确认与业务流程，不能因为检索层返回了一条规则就直接触发发布。

### 6.2.2 Context Access Layer

#### “能否发布”怎样经过五层，而不是在每层重复猜测

应用接到请求后，确定当前项目和运行，将可信身份交给访问层；访问层发现需要现行规范和实时审批，同时可读取表达偏好。服务层解释各对象资格：哪版规范有效，哪个偏好当前可用，业务工具能否查询该发布。

表示层提供明确字段，如规则人数、角色限制、来源版本和业务时点；存储索引层执行具体读取。返回时仍携带对象身份及缺口，不在最底层把所有数据拼成无出处字符串。访问层核对证据是否齐全，再为应用装配。

如果审批工具超时，应用收到的是“规则可用、当前状态未确认”，而非空白上下文；于是可以解释要求并停止许可判断。如果访问层拿不到对象版本，就无法识别缓存是否过期；如果应用擅自另查向量库，又会绕过公共过滤。

分层的价值是让每层都有明确判断及可传递结果，不是把同一个权限、时间和语义判断分散复制五次。契约能解释失败在哪里，才便于替换底层实现。

Letta Code 的核心文件投影和按需读取展示了访问时选择信息的价值。但它的路径组织不能替代本书多租户授权。接入其他系统时应明确哪些检查由适配器提供，哪些必须由公共访问层执行。[固定版本源码](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L65-L198)。

### 6.2.3 Knowledge & Memory Service Layer

服务层处理对象的业务生命周期：规范候选如何批准、偏好如何更正、检查点如何确认。它把数据库操作组织成有含义的动作，而不是只暴露通用增删改。

“保存了一条记录”和“新版规范已生效”可以是不同状态。接口应清楚承诺完成到哪一步，避免上层把部分持久化误认成整体发布。

分层接口应传递对象与证据标识，而不是只传一段拼好的文本。Context 层需要知道候选类型、版本与成本，才能选择；应用层需要知道不足项，才能决定是否询问或调用工具。底层若只返回裸文本，上层只能再次猜测这些信息。

表示层也不应成为所有策略的集合。它定义字段与约束，知识验证、记忆价值和运行恢复仍各有归属，防止通用 Item 演变成无法测试的万能对象。

### 6.2.4 Data Representation Layer

表示层定义 Source、Evidence、Item 与关联的字段和约束，使不同模块交换同一含义。例如 source_version 必须指不可变快照，而非实时网页。

字段升级要包含兼容、默认值和迁移规则。若一个模块把空范围理解为私有，另一个理解为共享，即使 JSON 都有效，系统仍会产生严重错误。

字段约定可以用一个升级事故说明：v1 没有 project_scope，某模块将缺失解释为“所有项目”，另一个解释为“尚未确认”。将旧记录直接传给新版，可能让私有偏好扩展到全部项目。安全的迁移应明确旧数据如何补齐、哪些暂不可用，并让契约拒绝不认识的关键状态；结构可解析不等于双方业务含义一致。

### 6.2.5 Storage & Index Layer

存储与索引层实现可靠写入、检索和必要事务，但不独自决定什么内容可被当成真值。主库负责对象版本与状态，索引提供候选，访问层核对最终资格。

替换索引产品时，检查查询过滤、删除确认和重建能力是否仍满足契约。接口兼容不代表一致性和治理语义完全相同。

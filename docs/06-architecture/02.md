# 6.2 系统逻辑分层

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

五层分别承担什么责任？

分层按照语义责任划分：应用表达任务，上下文访问组织输入，知识与记忆服务管理策略，表示层定义实体，存储索引层实现持久化和访问加速。

## 机制与细分考点

### 6.2.1 Application / Agent Layer

Application/Agent Layer 负责业务目标、规划和最终行动授权。它不能直接绕过服务去写索引或更改治理状态。

### 6.2.2 Context Access Layer

Context Access Layer 负责路由、预算与证据组装，返回材料与不足项；模型调用可以位于应用层或适配层。

#### 访问层负责把查询变成受约束计划

Context Access Layer 接收主体、任务和预算，先确定允许访问的域，再把请求路由到档案读取、知识检索及检查点查询。底层返回候选后，访问层统一处理可见状态与装配，避免每个 Agent 自己实现一套权限过滤。

Letta Code 的核心文件投影和按需读取展示了访问时选择信息的价值。但它的路径组织不能替代本书多租户授权。接入其他系统时应明确哪些检查由适配器提供，哪些必须由公共访问层执行。 [固定版本源码](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L65-L198)。

### 6.2.3 Knowledge & Memory Service Layer

Knowledge/Memory Service Layer 执行形成、验证、召回和演进策略，是业务规则归属点，而不是简单数据库转发。

### 6.2.4 Data Representation Layer

Data Representation Layer 定义 Source、Item、Evidence 与 Checkpoint 等类型，集中版本与约束，减少各模块解释不一致。

### 6.2.5 Storage & Index Layer

Storage/Index Layer 管理主记录、对象文件和派生索引。向上暴露能力接口与一致性边界，不泄露引擎细节给所有调用者。

## 推导与工程过程

分层接口应传递对象与证据标识，而不是只传一段拼好的文本。Context 层需要知道候选类型、版本与成本，才能选择；应用层需要知道不足项，才能决定是否询问或调用工具。底层若只返回裸文本，上层只能再次猜测这些信息。

表示层也不应成为所有策略的集合。它定义字段与约束，知识验证、记忆价值和运行恢复仍各有归属，防止通用 Item 演变成无法测试的万能对象。

## Atlas 案例

应用请求发布判断；Context 层协调规则、偏好与状态；服务层选有效对象；表示层提供统一记录；底层执行 SQL 与索引查询。

## 适用条件与局限

分层允许同进程实现，避免为每层引入不必要 RPC。

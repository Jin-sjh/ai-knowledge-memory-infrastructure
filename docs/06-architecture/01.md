# 6.1 总体架构原则

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。资料核验日期：2026-11-13。

## 要解决的问题

逻辑架构需要从一开始拆微服务吗？

先稳定职责、数据所有权与约束，再决定物理部署。单体可实现清楚的模块边界；多服务不能自动解决模型、权限和一致性问题。

### 6.1.1 逻辑职责与物理部署分离

#### 从一个进程拆成两个进程，哪些保证不能丢

初期一个应用内完成来源提交、派生任务登记和查询。后台处理变重后，可以先让构建任务使用独立工作进程，但主事实仍在可靠主库，输入和输出仍使用相同对象版本。拆分改变执行位置，不应改变谁有权发布当前知识。

在同库内，来源写入与待处理任务可放在同一事务；如果先写来源再向外部队列发送消息，进程可能恰好在两者之间崩溃，留下永远不被处理的输入。参考设计用同事务任务记录，再由投递器发送，消费者按事件标识幂等处理。这是解决特定失败窗口的方案，不是要求所有系统都搭消息中间件。

拆分后还要决定在线行为：索引未完成时是否按主记录读取，哪些查询可降级，治理事件如何优先传播。只将原函数变成 HTTP 调用，却没有这些约定，通常会增加中间态而非增强可靠性。

因此演进顺序是先明确逻辑责任和契约，再依据实际争用选择部署边界。服务数量不是验收指标；故障后是否仍能找到待处理对象、恢复并维持当前版本才是。

来源、记忆、检索和治理可以在同一应用中作为独立模块存在，不必一开始拆成网络服务。先明确哪个模块拥有对象、谁能修改状态、失败由谁恢复，再按负载决定部署。

例如向量构建耗时可交后台任务，在线读取仍在主应用；只有出现资源争用或隔离需求时再拆服务。方框数量不代表职责已经清楚。

LangGraph 在同一应用中区分 Store 与 checkpoint，说明逻辑独立不要求独立进程。本书推荐初期保留模块化单体，使用独立契约和数据表；拆分触发条件应是资源争用、故障隔离或团队责任，而不是架构图上的方框数量。[R16][固定版本源码](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/store/memory.ts#L188-L219)。

### 6.1.2 原始数据与派生数据分离

原始规范是可回查输入，Claim、Wiki 与向量是派生结果。保留来源快照与构建配置，意味着提取出错时可以重算，而不必把错误摘要当成唯一依据。

派生物必须登记输入版本。删除来源或改变权限时，系统才能定位受影响结果；仅保留相同文字而不保留依赖，会让治理失去可遍历路径。

### 6.1.3 存储、组织与访问解耦

存储决定数据怎样可靠保存，组织决定它以文档、命题或图关系呈现，访问决定本次任务取什么。一个关系型数据库也可以承载多种表示，向量数据库也不应替代业务授权。

解耦后可重建索引而不改业务身份，可增加图视图而不迁移全部原文。接口应引用稳定对象，不让应用依赖物理索引位置。

### 6.1.4 知识与记忆共享底座、独立策略

规则与偏好可以共用来源、时间和权限底座，但写入策略不同。规范靠有效发布关系确认，偏好靠主体表达与适用范围确认，不能统一为模型输出后直接覆盖。

共享的应是基础管理能力，不是抹平所有语义差异。服务层保留独立策略，联合访问层再组合已获得资格的结果。

### 6.1.5 可验证、可追溯和可演进

可验证意味着处理结果有检查方法，可追溯意味着能回到输入和配置，可演进意味着升级后仍能解释旧结果。三者可以用一条规则更新来检验：新版怎样发布，旧答案指向哪里，索引能否重建。

如果只展示一次正确回答，无法证明这些性质。参考架构要求版本化输入、阶段日志与回归用例，而非依赖人工记住每次改动。

模块化单体的边界可以通过依赖方向落实：应用依赖服务接口，服务依赖表示和存储端口，具体索引适配器实现端口。禁止跨模块直接改另一个模块的数据。此时未来替换索引或拆进程不需要重写业务语义。

拆服务前要回答谁拥有事务、失败由谁重试、权限在哪里核验。不能仅按图上五层拆成五个服务，否则原先一次本地调用会变成多个网络故障点而没有额外收益。

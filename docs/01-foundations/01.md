# 1.1 AI 系统的信息基础

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

模型已经知道很多，为什么还需要外部系统？

模型是条件生成器，外部系统提供可更新、可授权和可追踪的信息。它们通过本次推理上下文连接；保存成功并不意味着模型已经利用了信息。

下文用虚构的 Atlas 团队助手串联问题：它需要查询发布规范、遵循用户偏好，并在中断后继续同步文档。案例用于解释机制，情节与数值不代表实测。真实项目的实现则另附固定版本来源。

### 1.1.1 LLM 的参数化知识与非参数化知识

假设模型曾学习过“一人审批”的旧规范，而项目今天改成两人。训练得到的信息包含在参数中，应用通常无法像修改数据库行那样，直接定位并替换这一条知识。把新规范放进外部知识库，则可以独立更新来源、版本及可见范围，再在回答时读取。[R01]

两种信息可能同时影响回答：模型仍有旧的先验，输入材料提供新的规定。因此外部更新只解决“能提供什么”，还要让系统选到现行规范、说明适用时间，并检查生成是否遵循材料。

### 1.1.2 模型内部知识与外部信息系统

模型内部知识来自训练，外部信息则保存在文档、数据库等系统中。更新知识库里的文档，不会直接改写模型参数。在使用外部检索的助手中，应用需要把相关材料取出来，提供给模型，模型才能在本次回答中使用它。[R01]

例如，Atlas 的发布规范已经从“一人审批”改成“两人审批”，新规范也已经保存到知识库。用户问“现在发布需要几人审批”，一次正常处理是：

1. 应用查找当前有效的规范，取得“两人审批”的原文。
2. 应用把用户问题和这段规范一起放进本次模型输入。
3. 模型根据收到的材料回答，并引用对应规范。

第一步是从存储中取信息，第二步是让模型看见信息，第三步才是生成回答。因此，“新规范已保存”只完成了其中一部分，不能据此认为答案必然已经更新。

假如助手仍回答“一人”，可以沿这条过程定位：

| 检查发现 | 问题发生在哪里 | 接下来查什么 |
| --- | --- | --- |
| 知识库里仍只有旧规范 | 新内容尚未正确保存或发布 | 来源更新与有效版本 |
| 知识库有新规范，但模型输入里是旧规范 | 应用取错了材料，或复用了旧输入 | 检索、版本选择与缓存 |
| 模型输入已有正确新规范，回答却仍采用旧要求 | 模型没有正确使用材料，或输入中有未处理的干扰 | 完整输入及生成结果 |

这个区分有实际作用：取错材料时，应修复访问过程；材料正确却被误用时，再检查生成过程。继续往知识库添加文档，未必能解决这两种问题。

具体项目还会规定何时让保存的内容对后续调用生效。例如 Letta Code 的已提交记忆与工作区文件有不同读取边界，相关实现放在[同步写入与异步提炼](../03-formation/06.md)中分析。理解本节只需先掌握“保存 → 取出并提供 → 使用”这条过程。

### 1.1.3 无状态推理与有状态智能系统

这里的无状态是指一次推理调用本身不必保留前一次请求的应用记录。用户在第一轮说了项目名，第二轮只问“审批需要几人”，应用必须重新提供相关历史或从外部记录取得项目，才能让第二轮具备必要语境。

有状态的系统由应用管理会话、任务进度和持久记录。排查“助手忘了”时，要看应用是否保存、是否读取、是否装配到输入，不能把所有缺失都归结为模型记忆能力。

持久化边界同样关键：若 Agent 把任务状态只留在当前对话窗口，窗口压缩可能删除下一步执行所需的精确字段。外部状态存储并非单纯增加上下文长度，而是使恢复所需事实独立于模型本轮能看到多少文本。

### 1.1.4 AI Agent 对知识、记忆与状态的需求

Atlas 助手同时要回答规则、遵循个人偏好、继续同步文档。规则回答“允许做什么”，偏好调整“怎样表达”，同步游标决定“下一步从哪里执行”。三者可以参与同一次任务，却不能互相替代。

把它们都写成可检索文本，会让精确游标受到摘要和相似度选择影响。更合适的做法是分别保存受审核的规则、带范围的偏好和结构化检查点，在访问时组合。

### 1.1.5 外部知识与记忆基础设施的价值及边界

外部设施适合解决规范更新、历史保留、权限筛选和任务恢复等问题。例如用户撤回偏好后，可以阻止它再次进入上下文，而无需重新训练模型。

它不能仅凭“查到一段文字”保证答案正确，也不能替业务系统批准真实发布。要明确分工：信息层提供可用依据，生成层解释依据，执行层核对权限与动作前提，三者分别留下可检查结果。

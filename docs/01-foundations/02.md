# 1.2 核心概念体系

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

知识、记忆、状态和上下文分别是什么？

本书采用工程操作性定义：知识强调可复用陈述，记忆强调主体保留的历史，状态强调执行位置，上下文强调本次调用可见输入。分类服务于管理决策，不宣称唯一哲学定义。

### 1.2.1 Data、Information、Knowledge 的区别

一条日志里的“2”只是数据；附上“本次审批人数为 2”后才有明确语境；再与规范、人员角色和发布类型组织起来，才能支持“本次是否满足条件”的判断。变化在于语境和可用关系增加，不是数字经过加工就自动变真。

若原始日志把重复审批算成两个人，再精致的知识表示也会保留错误。管理系统应保留从观察到结论的关联，让人能回查计数方式和适用条件。

### 1.2.2 Knowledge、Memory、Experience 的关系

一次紧急发布经历包括发生了什么、采取了什么行动及结果。系统保存这段经历后，它成为可召回记忆；从多次经历归纳出的“某类故障先检查配置”可以成为知识候选。

但一次成功可能依赖当时环境，不能直接写成通用操作规则。把经验提升为知识时，应明确前提、验证方法和反例；正式规范也可能直接来自制度文件，并不都由个人经历归纳而来。

### 1.2.3 Context 与 Memory 的区别

用户的简短回答偏好已存在数据库里，却未必出现在本次模型输入中。记忆指跨调用管理的记录，上下文指这次调用实际看见的输入；前者经过选择、过滤与装配，才可能成为后者。

反过来，工具刚查到的当前审批状态可以只在本轮使用，不必长期保存。判断某内容属于哪里，应看它承担的职责，不能只按文本长度或保存时间区分。

### 1.2.4 State 与 Memory 的区别

#### 同一条消息为什么会产生不同对象

用户说：“Atlas 的普通发布需要两人审批，我希望你先给结论；同步任务已经完成前三页。”这段话至少包含规则陈述、偏好表达和任务进度声明。系统不能因为它们出现在同一条消息里，就赋予相同可信程度。

偏好可在核对主体和范围后成为默认候选；审批要求要与现行规范核对；同步进度则需要与实际提交记录对应，不能仅靠用户或模型摘要决定下一页。保存对象时保留原始消息，再分别建立有责任边界的表示。

| 对象 | 用来回答什么 | 不应承担什么 |
| --- | --- | --- |
| 规则对象 | 普通发布需要什么条件 | 证明本次审批已经完成 |
| 用户偏好 | 回答怎样组织 | 改写审批许可 |
| 运行检查点 | 下一步从哪里继续 | 证明远端副作用一定完成 |
| 本轮上下文 | 这次模型实际看见什么 | 替代长期来源与审计记录 |

这些对象可以引用同一消息，却具有不同更新和删除方式。设计分离的原因不是术语整齐，而是避免一个对象的压缩、过期或更正破坏另一个职责。

LangGraph 的仓库示例实际观察到 A 的 visits 为 2、B 为 1，而两者读取同一 Store 偏好。这里验证的是作用域与恢复分工；自然语言是否符合偏好仍需单独评测。运行代码与断言见[官方包示例](../../examples/projects/README.md)。[固定版本源码](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/store/memory.ts#L188-L219)。

数据模型应允许这种多用途，却避免概念循环：不能因为“保存在 Memory Store”就定义它是记忆，也不能因为“检索出来”就定义它是知识。分类根据用途和治理责任，而非组件名称。

### 1.2.5 Knowledge Base、Memory Store、Context Store 的区别

知识库管理可复用规则与文档；记忆存储管理主体的偏好和经历；上下文存储常用于保存已装配输入或缓存。它们可以共享同一数据库，差别主要在对象责任、更新和失效策略。

例如规范更新应使依赖旧规则的上下文缓存失效；偏好撤回应停止个性化使用；任务检查点却不能随普通缓存过期而丢失。先定义这些责任，再决定是否使用不同产品或数据表。

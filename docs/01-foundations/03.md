# 1.3 知识工程理论

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

知识工程为什么不只是搜索文档？

知识工程把来源转化为可表达、可验证、可维护的信息。检索只解决访问；出处、矛盾、失效和维护仍需额外机制。

### 1.3.1 Knowledge Engineering 的定义

知识工程要把“文档里有要求”变成“系统能在正确条件下使用这项要求”。以审批规范为例，需要确定来源、抽取人数和角色条件、表示普通与紧急场景、支持查询，并在规范变化后维护结果。

它关注整条知识处理链，不等于搭一个向量索引。若系统只能找到原文，适合称为检索能力；若要据此判断许可，还需要显式条件、证据和验证责任。

本书聚焦 LLM 外部信息管理，不展开专家系统与形式逻辑的完整历史。

### 1.3.2 知识获取、表示、组织、推理与维护

#### 从一段规范到一次可解释判断

原文规定“普通生产发布至少两名不同审批者，提交人不能审批”。用户报告当前有两条审批记录，并问能否发布。获取阶段保存的是规范快照与两条业务记录；表示阶段提取场景、人数和身份限制；组织阶段将它们关联到相同项目与发布；判断阶段计算的是两条记录是否来自不同且有资格的人。

假设两条记录都是同一人重复操作，检索已经找到正确规范，最终却仍应判断人数条件未满足。若系统只统计条目数量，问题出在业务状态解释；若规范被提成“任意两条记录即可”，问题更早出在知识表示。两者需要不同修复，不能统一归为模型答错。

维护阶段再接收新版时，旧结论也不能无条件延用：新规范可能改变角色限制，已有审批状态未必仍满足要求。知识工程因此把输入、表示、使用和维护连成一条可追踪链。只展示一个正确回答，看不到这些环节是否健全。

在团队知识库中，维护责任至少要落到某个领域所有者或审核角色。没有人能解释哪些规则已被替代时，增加自动抽取只会更快积累不确定内容。自动化应降低组织成本，而不是消除必要的责任归属。

### 1.3.3 知识工程与信息检索的关系

检索回答“哪些材料可能相关”，知识工程还要处理“这些材料支持什么、何时适用、变化后怎样维护”。用户询问普通发布时，检索到紧急例外只是一个候选，不等于找到了可直接采用的规则。

工程上可以先建设原文检索，再按业务风险增加命题审核和条件判断。并非所有问答都要建规则引擎，但凡输出会触发许可或执行，就需要明确相关性与有效依据的边界。

LlamaIndex 的 ingestion upsert 根据文档标识与哈希处理变化。它解决内容同步问题，不负责裁决规范是否正确。本书的知识层需要在节点之上增加命题条件、证据和审核状态；只有当业务确实需要这些判断时，才值得承担额外建模成本。[固定版本源码](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L469-L507)。

### 1.3.4 知识工程与传统知识管理的关系

传统知识管理常以人阅读文档为终点，读者自己判断版本、上下文和例外。接入 Agent 后，系统可能自动截取段落并据此行动，过去由人补足的判断必须显式化。

这不要求抛弃已有 Wiki。可以继续让专家维护页面，同时增加不可变版本、段落定位和审核状态；机器生成的摘要作为派生内容，不能悄悄取代原始规范。

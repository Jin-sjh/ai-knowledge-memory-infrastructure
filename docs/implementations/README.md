# 现有项目的实现案例

[全书首页](../../README.md) · [第三章](../03-formation/README.md)

理解机制时，需要看到它在真实系统中的调用入口、数据结构和执行顺序。本组案例逐项追踪官方源码，用同一个“用户从详细答复改为简短结论”的问题比较不同实现；文档摄取则使用发布规范说明。

| 项目 | 要观察的实现 | 阅读重点 | 核验方式 |
| --- | --- | --- | --- |
| [LlamaIndex](llamaindex.md) | 文档进入转换流水线，生成带来源关系的节点 | 输入收集、分块、元数据、转换缓存、更新策略 | 固定提交的 Python 源码 |
| [Mem0](mem0.md) | 新消息与旧记忆一起进入提取，再批量嵌入和追加 | 单次模型调用、精确去重、追加语义、失败路径 | 固定提交的 Python OSS 同步路径 |
| [Letta Code](letta.md) | 记忆写入文件，已提交的核心记忆进入系统提示 | MemFS 分层、Git 快照、延迟读取与上下文生效 | 当前仓库 MemFS v2 源码及提示 |
| [LangGraph](langgraph.md) | Store 管跨会话信息，检查点保存会话执行状态 | namespace/key、覆盖、thread_id 与持久化边界 | 固定版本官方 Node.js 包实际运行及源码 |

## 同一个变化，为什么不应预设相同实现

面对“以后项目问题先给简短结论”：

- Mem0 所读默认路径可追加一条包含变化背景的新记忆，不能假设一定覆盖旧记录。
- Letta Code 可由 Agent 编辑记忆文件，提交后在后续编译进入核心上下文；目录深处资料按需读取。
- LangGraph 提供 Store 的读写原语，应用决定写哪条键、何时更新；Store 本身不自动理解偏好。
- LlamaIndex 主要展示文档和节点处理，不能因为产生向量就认为已经完成偏好判断或事实验证。

这些不是四个同名 API 的比较，而是四种不同职责。不能将本书实验中的审核、事务和删除保证自动归给任一项目。

## 如何阅读源码引用

链接固定到具体提交并标出行号；核验日期为 2026-11-13。Mem0、Letta、LlamaIndex 的输入输出示意均根据源码解释，未实际执行其完整模型流程。LangGraph 的表格来自直接调用官方包，不使用本书的模拟 Store。

源码索引与核验范围见 [implementations.json](../../sources/implementations.json)。示例数据是本书编写的场景，不是上游项目的真实用户记录，也不构成模型效果或性能比较。

## 阅读与动手

建议先读 LlamaIndex 和 Mem0，了解数据进入系统后怎样处理；再读 Letta 和 LangGraph，区分上下文管理、跨会话存储与任务状态。需要观察候选审核和失败控制时，再运行 [Atlas 教学实验](../../labs/formation/README.md)。

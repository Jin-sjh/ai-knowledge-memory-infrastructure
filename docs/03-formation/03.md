# 3.3 知识提取（Knowledge Extraction）

[本章导读](README.md) · [可运行实验](../../labs/formation/README.md)

> 离线候选和语义判定由教材预设；程序负责结构与定位校验，不声称实现自动事实证明。

## 把“模型读懂了”拆成可检查的步骤

完整路径为：生成候选 → 定位证据 → 核对语义条件 → 判定候选状态 → 策略筛选。每一步需要不同证据。JSON 合法、有出处、值得保存和有权写入，不能合成一个“通过”标签。

### 3.3.1 实体与关系抽取

原文 mention 与稳定实体要分开。Atlas 是名称，atlas 是实验项目 ID；审批者是角色，不等于某个具体人。关系还需要方向和限制。

“提交人审批发布”和“审批者不可为提交人”涉及相同实体，但含义相反。因此实体出现不代表关系抽取正确。实验预设 ID，不实现实体消歧，也不把关系共现当作因果。

#### Mem0：事实文本与实体关联不是同一阶段

所读默认路径先提取并持久化记忆文本，再对成功写入的记录批量识别实体、维护实体到记忆的关联。它不是先构造一套经验证的知识图谱再允许写入。[实体关联阶段](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L1100-L1204)

因此，文本被识别为某个用户或项目的相关信息，并不意味着关系方向、事实真值或实体消歧全部完成。讨论“知识提取”时，需要把模型输出的文本和后续索引关联分开。

### 3.3.2 事实与 Claim 提取

Claim 是可验证命题候选，不是自动成立的事实。应保留主体、属性、值、条件和可读陈述。数值还需要单位、比较关系及适用范围，“至少两人”不同于“恰好两人”。

实验用 value 字符串和 conditions 数组表达部分语义，content 保留完整可读约束；这不是审批规则执行引擎。真正执行时，需要经过验证的领域谓词，不能直接从字符串 2 决定操作许可。

#### Mem0：先召回旧记忆，再提取新信息

以下是本书对源码的重述，不是复制原函数，也不是实际运行结果：

~~~text
新消息
  → 读取该作用域最近消息
  → 为新消息生成查询向量
  → 在同作用域召回最多 10 条旧记忆
  → 新消息、近期消息、旧记忆共同构造提示
  → 一次模型调用产生 memory 列表
  → 批量生成候选记忆向量
  → 对旧召回集和本批次做文本哈希去重
  → 批量插入向量记录
  → 给实际写入的记录追加历史、实体关联
  → 保存消息，返回 ADD 结果
~~~

对应的主要阶段在 [_add_to_vector_store](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L918-L1098)；[返回阶段](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L1206-L1220)只为落库成功的记录构造 ADD 结果。

注意实际调用只把部分上下文字段传给提示构造器，不能因为函数签名支持 summary 或 recently_extracted_memories，就假设每条调用都填充了它们。[调用点](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L920-L964) · [提示构造器](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/configs/prompts.py#L1016-L1062)

假设当前存储有“u1 喜欢详细解释项目问题”，新消息说“以后先给简短结论”。检索后的旧记忆会与新消息共同进入提取提示。这里的旧记忆用于提供上下文、去重与关系线索，不等于程序已经决定更新它。

提取器可能生成下面的结构。**这是按接口说明编写的示意，未调用模型，结果并不保证如此。**

~~~json
{
  "memory": [
    {
      "text": "u1 的项目答复偏好从详细解释改为先给简短结论"
    }
  ]
}
~~~

程序为新文本生成 embedding 和新的 UUID，附带 data、hash、created_at、updated_at 等字段，再插入向量存储。此路径没有根据这一变化自动把旧记录改成新文本。因此更准确的描述是“追加变化信息”，而不是“提取到矛盾后一定 UPDATE 原记忆”。[记录构造与插入](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L1007-L1076)

这意味着检索和上下文选择仍需要处理新旧表达。保留历史变化有利于追踪经历，但不能只凭 add 成功，就断言以后永远只召回最新偏好。

### 3.3.3 概念与规则提取

概念回答一个术语是什么，规则回答什么条件下允许或要求什么。普通与紧急发布共享审批概念，却不能平均成“通常一到两人”。

实验分别提取两条规则，保留生产环境前提；紧急规则增加当值负责人和 24 小时复盘。概念、事实与规则不必采用同样粒度，关键是保留足以独立验证和更新的条件。

#### LlamaIndex：生成 Node 还没有生成可信规则

NodeParser 主要产生结构与来源联系。若要实体、Claim 或规则，需要明确增加对应转换，并验证其输出。即使一个节点有 embedding、metadata 和来源 ID，也只说明它可以被管理和检索，不代表内容正确、条件完整或允许长期使用。

本书第三章的结构分块实验可以帮助理解这些边界，但它没有复现完整 LlamaIndex。读者应对照真实接口区分：框架提供了哪些处理钩子，应用还要补哪些领域规则、验证与权限控制。

### 3.3.4 跨文档知识融合

policy-mirror 与 policy 具有相同 origin_id，所以不能算作两份独立确认。实验保留两个来源，令相同规范化内容写入为 NOOP，并在审计保留镜像观测。

这里没有实现通用同义改写融合。两种措辞若表示相同命题，仍需独立判定和领域规范化；两条看似相似但条件不同的规则不能直接合并。矛盾规范交给第四章治理。

### 3.3.5 证据绑定及来源追踪

结构可定位检查包括：来源版本存在、块属于来源、quote 可逐字且唯一匹配。语义支持则要核对命题是否扩大或改变原意。

实验判定绑定 candidate_hash 与 source_hash。修改候选或完整来源后，旧判定不再匹配。哈希只帮助检测快照变化，不是签名或审核授权，也不能证明事实正确；前提是判定文件由可信控制面维护。[R07]

#### 来源可回溯不等于命题有充分证据

LlamaIndex 的节点位置和来源关系回答“这段文本从哪里来”，Mem0 的记忆记录保存提取文本及相关元数据；这些结构与 Atlas 的逐条命题判定解决不同问题。不能因为某项目提供 source 或 hash 字段，就认定它完成了本节要求的证据蕴含校验。来源定位的具体代码见[预处理中的节点分析](02.md)，模型输出的实际落库路径见[写入机制](06.md)。

## 正例：从表格行到候选

原文：

~~~text
| 普通发布 | 2 人 | 审批者不可为提交人 |
~~~

候选的完整结构如下，属于手写教学输入：

~~~json
{
  "id": "rule-normal",
  "source_key": "policy@1",
  "chunk_id": "policy@1#3",
  "quote": "| 普通发布 | 2 人 | 审批者不可为提交人 |",
  "type": "rule",
  "subject": "atlas",
  "predicate": "minimum_approvers",
  "value": "2",
  "conditions": ["普通发布", "生产环境"],
  "content": "Atlas 生产环境普通发布至少两名非提交人的审批者。"
}
~~~

生产环境范围来自来源另一段，而不是引用行本身。“不可为提交人”保留于 content，却还没有完整形式化进领域约束。这些差异需要诚实展示，不能用结构化外观掩盖缺失。

验证器先检查字段，再查来源和块，定位 quote，最后匹配场景判定。通过后状态为 SUPPORTED，尚未等于允许持久化。

## 反例：原文确实存在，为什么仍拒绝

vague-note@1 只有：

~~~text
发布前需要审批。
~~~

rule-hallucinated 却写“至少两人审批”。引用存在，JSON 合法，但 2 没有依据。本实验作者预设的语义判定将其拒绝为 UNSUPPORTED_NUMBER。substring 算法自身无法发现该语义错误。

如果删除预设判定，结果应为 NEEDS_REVIEW / NO_MATCHING_REVIEW，而不是自动接受。把正常候选 value 改为 999，引用仍存在，但候选哈希改变，不能复用旧批准。给规范加一句“以上仅供演练”，引用行不变，来源哈希仍会使判定失效。

## 为什么需要离线预设

固定候选让读者能分别扰动引用、值、主体和来源，定位错误究竟在哪一层。如果提取器和唯一裁判是同一模型，同样的误读可能反复通过检查。

预设 reviews 是教材编写者的情景答案，不是真实专家审核记录，也不是密码学签名。expected.json 独立列出预期决策，用来验证实现；它不是程序运行后自动生成的“正确答案”。

## 运行与观察

~~~sh
npm run lab:formation -- --stage extract
npm run lab:formation -- --stage verify
~~~

03-extract.json 标记 offline-fixture。04-verify.json 展示证据偏移与状态。quote-fabricated 返回 QUOTE_NOT_FOUND；scope-smuggling 夹带 scope 字段，返回 INVALID_CANDIDATE。实验不会默默删掉额外字段再当成功。

## 真实模型入口与边界

可选适配器按 Chat Completions 形式发送 messages；兼容服务是否支持模型及参数需单独核对。可配置 JSON mode，本地仍做 Schema 校验，JSON mode 不保证语义正确。[R13]

真实模式默认不加载教材预设判定来批准新输出。模型也不能返回 reviews 字段；未独立核验的候选停在待审核。详见[运行手册](../../labs/formation/README.md)。适配器经过模拟响应测试，尚未通过真实模型调用验证。

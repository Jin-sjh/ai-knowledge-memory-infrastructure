# 3.1 信息获取机制（Acquisition）

[本章导读](README.md) · [可运行实验](../../labs/formation/README.md)

> Atlas 的输入和场景判定均为合成教学材料。离线测试用于验证处理流程，不代表真实模型的提取效果。

## 为什么采集必须先于提取设计

形成机制的第一步不是让模型阅读所有材料，而是建立可复核的输入边界：拿到了什么、凭哪个身份拿到、属于谁、是哪一版、失败后怎样重试。来源丢失或权限混乱，不能靠后续更强的模型补救。

Atlas 将规范文档、用户对话和工具轨迹统一包装为 Source，但保留各自的形成方式。连接器负责身份、scope 和来源版本，模型只处理获准读取的正文，不能自填这些控制字段。

### 3.1.1 文档、网页及多模态数据

文档要同时保存原件、结构与定位。网页应关联抓取快照，图片和音频应保留 OCR/转写与原件位置的映射。原始不等于真实，只代表能复核当时输入；OCR 修正后的句子也是派生物，不能替代原件。

本实验直接读取文本和 Markdown 表格，没有实现网页抓取、PDF 解析或 OCR。真实系统可在相同来源契约前增加适配器，但要重新验证表头、脚注和否定词是否丢失，不能把适配器返回了字符串当成解析正确。

#### LlamaIndex：文档输入先进入摄取流水线

IngestionPipeline.run 先收集传入 documents、nodes、构造时配置的 documents，以及 readers.read() 返回的内容。之后选择文档重复处理策略，运行 transformations，再把带 embedding 的节点交给 vector_store，最后更新 docstore。[输入汇集](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L429-L449) · [运行流程](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L572-L662)

按源码概括：

~~~text
Document / Node / reader 输出
  → 文档 ID 与 hash 检查
  → SentenceSplitter 等转换
  → 可选提取器、embedding 等后续转换
  → 有向量的节点进入 vector_store
  → 更新文档存储与 hash
~~~

转换顺序由调用方配置。默认转换包含 SentenceSplitter 和配置的 embedding 模型；不能因只是运行 ingestion，就假设一定不产生外部模型调用。[默认转换](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L423-L427)

### 3.1.2 用户对话与交互记录

对话至少保存消息作者、时间、主体和会话范围。用户本人说“以后”可成为长期偏好候选；引用别人说的“以后”不等于本人意图。一次性要求与长期意愿也不能只凭文本长度区分。

actor 和 scope 在实验中来自可信配置。explicit_long_term 等元数据是教材给定的场景判定，不是已经实现了自动意图识别。真实接入需要认证来源和可审核的授权判断。

#### Mem0：为对话建立作用域后再读取近期消息

在所读 Python OSS 同步路径中，Memory.add 会将字符串转为 user 消息，再按 user_id、agent_id、run_id 构造作用域。提取阶段先读取同作用域最近 10 条消息，用来帮助理解新输入的指代，而不是把每条消息当成完全独立的文本。[消息与作用域处理](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L820-L940)

这里的作用域来自调用参数。应用仍须先确认调用者身份；函数接收 user_id 并不能证明调用者有权代表该用户。模型后续参与内容提取，不应负责给自己分配数据访问范围。

### 3.1.3 Agent 行动轨迹和工具结果

#### 工具说成功，采集端究竟拿到了什么

假设同步工具返回 success，但没有给出远端对象 ID，目标列表回查也没有新增文档。采集端可以保存“工具返回了成功标记”这个观察，却不能升级为“远端文档已创建”。请求、工具陈述与目标状态是三种不同证据。

参考事件保留调用身份、目标、输入版本、开始与结束时间、原始返回以及回查状态。没有确认的副作用记为未知，交给恢复机制继续核对；不能只把一段成功总结写入长期经验。

这也是采集与理解的边界：采集尽量忠实保存实际观察，提取阶段可以提出“同步可能已完成”的候选，验证阶段再看是否有结果支持。如果第一步就把工具标签改写成确定事实，后续无论如何检查引用，都只能忠实引用这个失真的输入。

必须区分传输成功、业务动作成功与目标状态确认。Atlas 的工具返回 transport_status=success，同时 readback_status=missing。前者不能证明同步目标完成。

采集时保留参数、状态、目标对象和验证结果，让后续检查能看见矛盾。若只摘出 success，再让模型总结“已成功同步”，就会把接口行为变成错误任务经验。

### 3.1.4 外部 API 与业务数据库

增量采集可依赖稳定游标、更新时间或变更序列。原则是来源快照可靠保存后再推进游标：先推进后保存，崩溃可能漏数据；先保存后推进，最多产生可识别重复。

还应采集删除和权限变化，否则只比较内容哈希会漏掉正文没变但已经撤权的来源。本实验从 JSON 读取完整事件批次，不模拟网络游标、CDC 或生产恢复。

#### LlamaIndex：同 ID 文档的更新要看存储配置

在同时配置 docstore、vector_store 并选择 UPSERTS 时，代码按 ref_doc_id（缺失时用自身 ID）查旧 hash：

| 情况 | 源码路径中的处理 |
| --- | --- |
| 没有旧 hash | 加入待处理集合 |
| 同 ID、同 hash | 跳过 |
| 同 ID、hash 改变 | 删除旧引用文档及对应向量，再重新处理 |

对应代码见 [_handle_upserts](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L469-L507)。如果只有 docstore 而没有 vector_store，这个提交会告警并在本次运行退回 duplicates_only；不能仅写一个 UPSERTS 参数就宣称更新链已经生效。[策略选择](https://github.com/run-llama/llama_index/blob/baeabbfe26241a6916e13e2a8c8156a02e0602cd/llama-index-core/llama_index/core/ingestion/pipeline.py#L574-L604)

先删旧向量再做后续转换，也不意味着跨存储事务或原子切换。转换失败的可用性、回滚和一致性需要在实际部署中设计。UPSERTS_AND_DELETE 还具有删除缺失文档的意图，不应不加分析地用于只提供部分文档的增量批次。

### 3.1.5 来源标识、去重及权限继承

来源 ID 与版本识别快照，哈希检查同一版本是否变化。权限域、作者和保留条件同样影响快照语义，不能只哈希正文。正文相同的两个租户对象也不能合并成公共对象。

实验对同版本同快照记一次重复；同版本内容或控制元数据发生变化则报 SOURCE_VERSION_COLLISION。生产系统应解释变更并产生新版本或权限事件，不能简单忽略冲突。

#### Mem0：身份字段不从自由 metadata 继承

入口接受 messages、user_id/agent_id/run_id、metadata 和 infer。至少需要一个身份作用域；自由 metadata 里的身份键会先清理，再由显式参数设置。它提供作用域组织，但调用者是否真的有权使用指定 user_id，仍需应用认证。[作用域代码](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L314-L404)

这个实现把内容附加信息与身份作用域分开处理，值得借鉴。但它不替代应用认证，也不自动提供所有下游索引的权限治理。

## 完整案例：15 个采集事件为何只得到 12 个来源

原始材料见 [atlas.json](../../labs/formation/fixtures/atlas.json)。当前身份为 u1，可读取 tenant-demo/project/atlas 和 tenant-demo/user/u1，写入范围另由 writable_scopes 表达。

| 输入 | 结果 | 原因 |
| --- | --- | --- |
| 规范、镜像、允许的对话和工具记录 | 12 个来源进入后续处理 | 格式及读取范围合法 |
| policy@1 再投递一次 | 记录 1 次重复，不新建来源 | 来源键和快照哈希一致 |
| u2 的个人消息 | SOURCE_NOT_AUTHORIZED | 当前身份无该个人作用域权限 |
| 空文本事件 | INVALID_SOURCE | 没有可处理内容 |

注意 policy-mirror@1 并非采集重复：它有不同来源 ID，仍需保留出处。但是镜像和原件的 origin_id 都是 policy，后续不能算作两个独立佐证。采集去重和证据独立性是两个问题。

实验不会让提取模型决定哪些作用域可见。越权消息在模型输入构造之前已被排除。来源是否可信、陈述是否正确，则留在后续验证阶段。

## 动手运行与反例

~~~sh
npm run lab:formation -- --stage acquire
~~~

查看 .lab-runs/formation/01-acquire.json 中的 sources、duplicates 与 rejected。单独运行 acquire 不调用模型，不执行后续写入。

复制实验输入，将重投 policy@1 的正文多加一个字符，再运行：

~~~sh
npm run lab:formation -- --input your-fixture.json --stage acquire
~~~

预期得到 SOURCE_VERSION_COLLISION。不要为让实验通过而覆盖第一次输入：同一版本不能同时代表两份不同内容。

## 这段实现没有保证什么

来源账本只在本进程及诊断快照中存在，没有持久化游标或分布式采集事务。真实系统还需要凭据管理、权限刷新和数据保留机制。

合成案例中的“不要保存”会阻止长期 Item 写入，但诊断快照仍保存原始合成输入。因此本实验不能直接处理真实私密对话，也不能被解释为已满足原始日志的删除和保留要求。

# 3.4 记忆提取（Memory Extraction）

[本章导读](README.md) · [可运行实验](../../labs/formation/README.md)

> 场景中的意图与审核判定为教材预设。实验验证处理流程，没有测量真实对话的记忆提取准确率。

## 保存一句话之前，需要理解它服务什么未来任务

记忆形成不只是把对话总结成事实。系统要判断主体、持续时间、作用范围、保存意愿和未来用途。一次请求、长期偏好、事件经验和运行状态可以同时出现，却不能采用同一写入策略。

## 现有项目如何实现

Letta Code 的 MemFS v2 让 Agent 将长期信息组织到文件中：根级核心内容通过已提交的 Git 快照进入提示，项目细节则在目录索引下按需读取。LangGraph 则提供跨会话 Store，由应用决定提取、写入和更新。两者不是同一种自动偏好提取器。详见 [Letta 的文件与提示机制](../implementations/letta.md)和 [LangGraph 的真实运行结果](../implementations/langgraph.md)。

### 3.4.1 用户偏好识别

偏好需要主体、属性、值、任务范围、时间和明确程度。用户说“以后回答项目问题时先详细解释原因”，只约束项目问题，不代表所有场景都要长篇回复。转述别人的偏好也不能自动归到当前用户。

实验的 explicit_long_term 来自可信场景元数据，不是模型检测到“以后”就获得保存权。隐式推断与明确陈述要分开，用户后来更正时应能定位并修订原偏好。

### 3.4.2 事件与经历提取

事件保存何时、谁做了什么及结果，不能只留下总结者的解释。用户陈述、工具观测和系统推断需要明确来源类型。

个人知识助手记录一次阅读或收藏，最多证明发生了该动作，不能自动推断用户认可全文或形成稳定兴趣。TypeScript 案例正用于说明“本次选择”不足以支持“永久偏好”。

### 3.4.3 Agent 任务经验提取

经验需要环境、行动和结果的关联。tool-success 的返回码成功，但目标回查缺失，不能据此形成“同步已经完成”的成功经验。

如果错误经验被长期召回，Agent 可能在以后跳过检查。采集完整轨迹和明确结果证据，比只保留一段积极总结更有价值。本实验拒绝该成功断言，而不按出现 success 的次数强化它。

### 3.4.4 操作策略与程序性经验提取

程序性记忆需要前提、步骤、验证方式、退出条件和副作用约束。Coding Agent 在演练环境重试后页面出现，只支持一次环境内的经历，不支持生产环境可以无限重试。

实验中的 procedure 即使证据定位正确，也需要独立验证。策略可用性不能只靠原文描述一次成功；还要检查幂等性、环境差异、失败反例和可恢复性。

### 3.4.5 临时状态与长期记忆的区分

一次性要求服务当前任务，检查点支持精确恢复，长期记忆支持未来复用。它们可以引用同一事件，但需要不同保存与访问策略。

“同步到第三页”的精确游标不能被随意压缩为“做了一部分”。本实验只标记 TRANSIENT 路由，不实现会话状态服务；长期生命周期由第四章处理，运行检查点由第六章处理。

## 完整案例：三句话、同一个属性、不同后果

| 用户原话 | 解释 | 实验结果 |
| --- | --- | --- |
| 以后回答项目问题时，请先详细解释原因 | 明确且限定范围的长期偏好 | 新增偏好 v1 |
| 这次回答请简短一点 | 本次要求 | TRANSIENT，不覆盖 v1 |
| 以后回答项目问题时，改成先给简短结论 | 同范围的长期更正 | 创建偏好 v2 |

“这次”和“以后”是重要线索，但引用、反讽和否定可能改变含义。实验没有实现一个普适语言分类器：它明确给定范围判定，再验证后续是否正确执行。

更正使用同一逻辑键，保留旧版并创建新版。随后再发送 expected_version=1 的旧命令时，当前已经是 v2，写入返回 VERSION_CONFLICT，防止过时视图覆盖新状态。

## 个人知识场景：真实说过也不代表允许保存

pref-denied 原文说“我偏爱深夜工作，但这句话不要保存”。即使提取的偏好本身得到场景支持，仍被 RETENTION_DENIED 阻止进入长期 Item。

pref-inferred 则只记录为一份笔记选择 TypeScript 示例。候选扩大为“永远偏好 TypeScript”，没有独立判定，因此为 NEEDS_REVIEW。频繁行为可作为后续核验线索，不能悄悄改写成用户已经确认的身份属性。

诊断快照仍含这些合成输入，故本实验不等于实现真实用户的完整保留授权。真实系统还要治理原始日志、模型供应商传输和派生缓存。

## Coding Agent：一条排障经验还缺哪些条件

coding-trace 记载演练环境重试同步后页面出现，尚未验证生产环境或重复提交安全。升级成程序性记忆前，需要回答：

1. 远端第一次确实失败，还是只丢失本地确认？
2. 重试会不会创建两份对象，是否支持远端幂等键？
3. 版本、权限、数据规模及环境是否相同？
4. 是否有独立重复验证和失败反例？

没有这些信息，应保留事件和待核验建议，而不是保存“失败就重试”。程序性记忆也不直接授予工具执行权，应用仍需单独授权。

## 删除请求应进入治理，而非成为偏好值

pref-delete-request 表达删除意图。实验为定位目标复用答复偏好的键，但 DELETE 被转换为 deletion_requested 事件，并未把 delete_requested 当新偏好保存。

这一步返回 DELETE_REQUESTED，旧偏好仍在内存里。删除屏障、副本清理和恢复重放属于第四章的治理协议，不能仅因收到请求就承诺已经删除。

## 动手检查

~~~sh
npm run lab:formation -- --stage select
~~~

比较 05-select.json 中 pref-detailed、pref-temporary、pref-brief、pref-no-save 与 pref-inferred。尝试删除某个预设判定：应停在待审核，不能因为候选措辞明确就绕过判定。

再观察写入轨迹，解释为什么临时要求不产生版本、明确更正产生第二版、旧命令产生冲突。能解释这些差别，比让脚本输出更多记忆更重要。

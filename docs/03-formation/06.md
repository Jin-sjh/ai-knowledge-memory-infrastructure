# 3.6 信息写入机制（Write Pipeline）

[本章导读](README.md) · [可运行实验](../../labs/formation/README.md)

> 运行代码是单进程、内存中的事务模拟。JSON 诊断快照不是持久化数据库，不保证崩溃恢复或多进程并发安全。

## 模型输出不能直接成为数据库操作

写入是受权限、版本和幂等约束的状态变化。已提取、已支持、值得保存和已经提交分别是不同阶段。本节跟踪 18 条写入命令，观察哪些创建版本、哪些被拒绝、哪些只返回历史回执。

### 3.6.1 Structured Output

合法 JSON 仍可含错误人数、错误主体和遗漏条件。实验以 candidate.schema.json 限制候选字段，拒绝额外 scope，并在真实模型入口后复用同一检查。

可选 JSON mode 也不保证命题语义或全部字段约束，是否支持取决于具体接口与模型。适配器不在失败时默默放松检查，截断、拒答、非 JSON 和非法外层结构都会停止。[R13]

#### Mem0：JSON 输出后仍有解析与失败分支

Mem0 调用模型时请求 json_object，随后清理代码围栏、尝试解析 memory 列表，失败时再尝试提取 JSON。模型调用异常会抛出 LLMError，而解析失败在所读实现中会变为空候选。调用者必须区分模型不可用、解析失败和确实无内容这几种情况，不能只看最终空列表。[调用与解析](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L957-L991)

这也说明结构化输出不是一次请求参数就完成的保证；程序如何处理不合规结果仍会改变外部行为。

### 3.6.2 Write Policy

写入接收已通过策略的候选与可信控制面命令，模型不生成可执行数据库权限。命令包含 event_id、candidate_id、operation 和 expected_version；写入再次检查 writable_scopes。

候选及来源哈希在写前复核，防止审核后改变内容。哈希不是认证：真实服务仍须保护判定文件和命令入口，不能让任意调用者构造一个 ACCEPTED 对象。

#### LangGraph：存储原语不代替写入策略

InMemoryStore 允许按 namespace/key 直接 put 值，存储层没有本书候选审核的概念。应用需要先决定这条信息是否适合保存，再调用写入。官方包的具体调用和同键覆盖见[记忆实现技术](../07-engineering/03.md)，不能将教学实验中的 Write Policy 当作框架内置流程。

### 3.6.3 ADD / UPDATE / NOOP / DELETE

ADD 要求对象此前不存在，UPDATE 要求基于已有版本创建后继。NOOP 只对相同规范化内容成立，显式要求 NOOP 却内容不同会冲突。

DELETE 在实验里转为 DELETE_REQUESTED 和 deletion_requested 待办，只交接治理，不删除记录。用户身份与明确删除依据仍需单独检查；普通知识来源不能靠换 operation 获得删除权。

#### Mem0：不能从旧提示推断当前写入动作

这个提交仍保留名为 DEFAULT_UPDATE_MEMORY_PROMPT 的提示和独立 update/delete 方法，add 的说明文字也保留更新、删除的描述。然而当前默认实现调用的是 ADDITIVE_EXTRACTION_PROMPT，提示构造器明确面向追加，最终结果返回 ADD。

所以必须从入口追到真正被调用的函数，而不能只搜索到含 ADD/UPDATE/DELETE/NONE 的提示就认定它仍是默认写入机制。[默认提示选择](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L942-L964) · [旧提示定义](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/configs/prompts.py#L176-L185)

同样，提示中提到 linked_memory_ids，并不能单独证明该字段会作为每条记忆间的关系落库。所读记录构造段主要消费 text 和 attributed_to；实体关联另有流程。要宣称具体关系持久化，必须继续追踪消费字段与存储实现。

### 3.6.4 同步写入与异步提炼

主记录、回执与 outbox 应处于同一提交边界，索引与摘要可异步跟进。主记录提交不等于所有视图立刻可见，接口需要表达这段差距。

实验把这些字段放在同一克隆状态中一次返回，并未实现真正消息消费者。生产消费者要核对对象版本、删除及撤权状态，旧任务成功不代表有权发布旧内容。

#### Letta Code：写文件、提交与进入上下文是不同状态

提示编译器先取得 Git HEAD，列出该提交里的 Markdown，再从 HEAD 对应路径读取文件内容，而不是直接把所有工作区修改都编入提示。[快照读取](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L65-L142)

v2 投影将根级核心文件的内容写入核心记忆区，同时提供子目录入口；再把结果插入原系统提示中的核心记忆位置。[根级投影](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L154-L198) · [提示注入](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L432-L460)

因此，“磁盘文件已编辑”“变更已提交”“新提示已编译”“模型已在某次调用看到它”是四个不同状态。提示模板也明确区分当前轮与后续重编译。本节不分析所有重编译触发器，不能据此声称任意编辑都会在下一 token 自动生效。

### 3.6.5 失败重试、幂等和事务边界

#### 写入成功不是一个覆盖全部阶段的布尔值

候选已通过审核，主记录提交为 v3，但历史记录或向量更新失败时，需要分别确认哪些结果真实存在。若统一返回失败，客户端可能重新生成对象；若统一返回成功，下游又可能以为历史和检索均可用。

参考设计把提交、索引和附加关联分开记录：主记录成功后返回稳定身份与版本，未完成派生任务继续重试。请求重放先查已有结果，避免重复业务对象；对象被更正或删除后，旧任务不得再发布为当前内容。

Mem0 的批量插入及逐项回退展示了部分成功的实际处理路径，但该路径本身不证明所有外部副本原子提交。应用若承诺更强一致性，应增加自己的协调与访问屏障，并明确代价。对于结果未知的外部操作，先回查再重试，不能把超时等同未执行。

幂等键识别是否同一请求，预期版本防止过时状态覆盖。相同键不同负载是 IDEMPOTENCY_CONFLICT；不同键但旧版本是 VERSION_CONFLICT。

实验通过“克隆—修改—返回替换”模拟事务，提交前异常不改变输入状态。它不保证多进程 compare-and-swap、真实持久化或跨库 exactly-once；数据库实现需要事务与约束保护。[R11]

#### Mem0：批量写入回退不等于跨存储事务

模型调用异常会抛出 LLMError；提取结果解析失败在当前实现中则被处理为空候选。这两种情况不能混为“没有发现值得保存的内容”。批量嵌入与插入分别有逐条回退；历史记录写入失败会记录错误，不能把它描述成向量库与历史库的统一原子事务。[调用与解析](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L957-L991) · [持久化和历史](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L1047-L1098)

因此即使向量记录已写入，也可能需要单独处理历史或派生关联的失败。这个实现与 Atlas 的主记录/outbox 事务模拟不同，不能借教学模型为上游项目增加它未提供的保证。

## 从具体命令开始

~~~json
{
  "event_id": "write-rule",
  "candidate_id": "rule-normal",
  "operation": "ADD",
  "expected_version": 0
}
~~~

空存储当前版本为 0。成功后产生规则 v1、index_requested 事件和请求回执。逻辑键由 scope、subject、predicate 与 conditions 组成，指纹比较经审核候选的语义字段。

这是教学 Item 投影，并非第二章完整 Schema。它没有完整的有效时间、治理账本和迁移机制；升级为服务时应显式映射，不能因字段名字相似就视为完全兼容。

## 完整轨迹：18 条命令的关键结果

| 事件 | 结果 | 要保护的不变量 |
| --- | --- | --- |
| write-rule | ADD，规则 v1 | 主记录和待办一起提交 |
| write-emergency | ADD，独立规则 v1 | 条件不同，不丢例外 |
| write-mirror | NOOP | 不增内容版本，保留来源审计 |
| write-pref-long | ADD，偏好 v1 | 明确长期意图 |
| write-pref-temp | BLOCKED / SESSION_ONLY | 一次性要求不污染长期偏好 |
| write-pref-short | UPDATE，偏好 v2 | 更正保留前后版本 |
| write-pref-stale | CONFLICT / VERSION_CONFLICT | 已有 v2，旧预期 v1 不覆盖 |
| request-delete | DELETE_REQUESTED | 只交接，不承诺删除完成 |
| write-rule 重投 | 原 ADD 回执，replayed=true | 不再创建记录、事件或审计 |

其他命令因无权来源、证据不足、未审核或禁止保存被阻止，完整结果见[实际离线轨迹](../../labs/formation/fixtures/recorded-run.json)。

最终状态有 3 个逻辑对象、4 个内容版本、5 个待办事件。普通与紧急规则各一版，偏好两版；4 个请求索引，1 个请求删除。删除后偏好仍存在，正是这个实验没有执行完整治理的明确边界。

## 三种重复，不同处理

相同事件、相同请求哈希：返回第一次结果。相同事件键却修改操作：冲突，不猜测是否想更新。不同事件但规范化内容一致：NOOP，留下新的审计观测。

回执返回的是历史操作结果，不保证当前仍是该版本。若需要当前值应另行读取。实验回执无限留在内存；真实系统需规定保留窗口，过早清理可能让迟到重试再次产生副作用。

键包含租户、事件 ID 和策略版本，请求哈希还绑定来源、候选与调用主体。读取许可不会自动成为写入许可。

## 事务原子性的最小可观察实验

writeCommand 在 next 克隆中创建版本、outbox、审计和回执，最后统一返回。测试在提交前主动抛错，原 store 的所有部分必须不变。再次提交相同命令，才产生一组完整结果。

如果把这段流程改成先读数据库版本，再无事务地分别写几张表，两个进程可能同时通过校验。生产实现需使用唯一约束、锁或原子版本比较，不能把内存顺序执行当并发正确证明。

索引成功但消息确认前崩溃，也可能重复执行。消费者应按对象/版本确定性键处理。真正外部副作用则需要远端幂等、回查或补偿，不由 outbox 自动解决全部问题。

## 运行并解释失败

~~~sh
npm run lab:formation -- --stage write
npm run test:formation
~~~

查看 06-write.json 和测试结果。重点不是有多少条成功，而是能解释每个拒绝：为什么临时要求不能 UPDATE 长期偏好；为什么旧版本冲突不能无限重试覆盖；为什么 DELETE_REQUESTED 不能对用户说“所有副本已删除”。

可选模型适配器的测试使用模拟响应，覆盖传输错误、HTTP 错误、截断、拒答与非法 JSON。它们验证失败路径，不代表已调用真实模型或测得提取质量。

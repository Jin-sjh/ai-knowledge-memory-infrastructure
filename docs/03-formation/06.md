# 3.6 信息写入机制（Write Pipeline）

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

怎样可靠执行写入？

流水线执行结构验证、证据检查、授权和价值判断、版本比较、事务提交与索引任务发布。模型提出建议，服务端执行最终动作。

## 机制与细分考点

### 3.6.1 Structured Output

Structured Output 只保证结构形式，服务仍需验证主体、来源和语义，不能把 JSON 合法当作事实正确。

### 3.6.2 Write Policy

Write Policy 检查写权限、价值与审核要求，记录策略版本解释不同时间的处理差异。

### 3.6.3 ADD / UPDATE / NOOP / DELETE

ADD 建对象，UPDATE 产生后继版本，NOOP 表示重复或无需变更，DELETE 发起治理；模型建议删除不等于有删除权限。

### 3.6.4 同步写入与异步提炼

同步用于主记录与即时更正，异步用于提炼和索引。异步任务携带输入版本，旧结果不能覆盖新状态。

### 3.6.5 失败重试、幂等和事务边界

幂等键包含租户、来源事件与策略版本；预期版本控制并发。主记录与 outbox 同事务提交，消费者幂等并分类重试。

## 推导与工程过程

在一个主库事务中先查幂等结果，再比较预期版本，创建内容版本、更新当前指针并追加 outbox；提交后返回主记录结果。消息消费者用事件 ID 去重，加载目标版本检查仍需构建，再写派生产物。若消费者写完索引但确认消息前崩溃，重复处理应覆盖相同确定性键，而非再插入一条。

这保证的是可重试和不静默覆盖，不保证全球意义的 exactly-once。跨服务副作用仍需单独的幂等键、查询确认或补偿机制。[R11]

## Atlas 案例

偏好由详细变简短：新建后继版本，标记旧版替代，并在同一事务写 outbox。索引稍后更新。

## 适用条件与局限

跨数据库与向量库通常没有单个本地事务，要明确主记录成功与索引可见的差距。

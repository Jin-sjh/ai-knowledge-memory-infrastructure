# 7.3 记忆实现技术

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

记忆系统从哪里开始实现？

先实现主体、有效时间、来源、更正与精确读取，再加入语义召回。没有治理的向量集合无法可靠回答哪条偏好当前有效。

## 机制与细分考点

### 7.3.1 原生数据库记忆实现

原生数据库用表或集合管理偏好、事件与版本，提供事务和可解释查询，是建立基线的直接方法。

### 7.3.2 Profile / Episodic / Procedural Store

Profile 保存当前偏好视图，Episodic 保存时间线，Procedural 保存带条件步骤；视图共用证据但维护策略不同。

### 7.3.3 基于向量检索的记忆系统

向量检索有助于发现相似经历，仍需主体、时态和权限过滤。更新需删除或失效旧向量，并防止异步结果复活。

### 7.3.4 Memory Framework

Memory Framework 可封装提取、召回和集成；评估时核对授权、导出、删除、版本和可替换性，而非只看演示。

### 7.3.5 Agent Runtime 集成

Runtime 集成应使用适配器并记录运行 ID；推理可读取记忆，写入由单独策略控制，避免把每轮中间想法永久保存。

## 推导与工程过程

偏好当前视图可由事件链投影：按主体和属性读取候选，过滤删除与权限，按有效期选择当前明确版本；程序性方法则先匹配环境前提。它们都不需要先通过向量相似度才能取得正确记录。向量主要用于不确定措辞和类似经历发现。

框架接入应通过适配器，把本书对象 ID、来源与删除任务映射到框架能力。若不能保留这些字段，应先评估差距而非在接入后才发现无法导出或纠错。

## Atlas 案例

用户偏好用确定性查询读取，故障经历用语义召回，程序性方法按环境条件过滤后再排序。

## 适用条件与局限

不对特定记忆框架作未经版本核验的能力保证。

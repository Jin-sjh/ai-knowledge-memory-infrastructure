# 7.1 数据库与持久化技术

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。资料核验日期：2026-11-13。

## 要解决的问题

各种存储各自适合什么？

以主记录、原始对象和派生访问结构选择存储。默认先用关系库管理版本与事务，按实测需求引入其他引擎，避免为每个语义类别配一个数据库。

### 7.1.1 关系型数据库

#### 同一业务对象在不同存储里各留什么

以规则 rule@2 为例，主库保存身份、批准状态、有效期和来源引用；对象存储保存手册原件；向量索引保存可检索文本及 rule@2 引用；图视图保存经验证的角色或依赖关系。每种存储保留的是不同职责，不应各自独立宣布哪个版本当前有效。

更新时先在主事实层确定目标版本，再构建派生视图。索引失败不能使已批准的新规则凭空消失，也不能让旧规则继续作为当前许可依据；可以按产品需要走精确读取或提示索引未追平。

恢复顺序也由此决定：先恢复主记录和治理事件，再恢复原件可用性，再重建索引。若只备份向量而丢失原始文本与对象状态，就不能可靠解释来源、重提取或防止删除信息复活。

选择统一存储时，关注是否简化了事务和恢复；增加专用存储时，说明它承担的查询收益，以及新增的同步、清理和备份责任。产品名称不能代替这些边界。

关系型数据库适合需要明确对象身份、版本、约束与事务的主记录，如当前偏好、规则状态和删除任务。可以通过唯一键、条件更新及关联表表达部分完整性要求。

它不自动判断文本真伪，也不意味着所有索引都与主库同时提交。先确定主事实与事务范围，再决定向量及其他视图如何异步追平。

技术能力核验日期为 2026-11-13；部署时应锁定版本并重新跑目标数据测试。

### 7.1.2 JSON / Document Store

文档存储便于承载类型多、字段变化的记录，例如不同经历拥有不同环境属性。灵活结构减少迁移负担，但也容易让同一字段出现多种含义。

仍需 Schema 版本、必需身份与时间字段，以及跨对象校验。不能因数据库允许任意 JSON，就把权限、有效期和状态约定交给各调用者自行猜测。

### 7.1.3 Object Storage

对象存储适合保存原始文档、解析产物和大附件，主库保存其身份、版本、哈希和权限引用。上传完成后确认对象可读，再发布来源记录，避免生成无法取得原文的证据。

大文件删除与主库状态变化可能不同步。在线读取先检查当前资格，清理任务再处理对象及副本；下载链接本身也要受访问控制。

### 7.1.4 Event Store

事件存储保留发生顺序与原始事实，例如表达偏好、更正和撤回。当前视图按事件重放或增量计算，便于追踪变化，但投影延迟和重放成本也要管理。

事件不可随意改写不代表不受删除要求约束。含敏感信息时要明确保留政策，并区分业务更正、停止使用和物理清理。

这增加了数据协同成本，只有需要历史、更正或审计时才值得采用。Mem0 的追加路径与 LangGraph Store 的同键覆盖分别体现不同存储语义；二者都不能独立证明系统具有完整事件溯源能力。[R14][固定版本源码](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L918-L1098)。

### 7.1.5 Vector Database

向量数据库提供相似候选检索，适合不确定措辞与经历发现。它应保存业务对象引用与必要过滤字段，而不是成为唯一事实来源。

选型检查过滤是否前置、更新删除何时可见、结果能否绑定版本及索引能否重建。大规模检索快，不代表当前偏好精确读取或业务事务也适合放在这里。

主库、对象存储和索引有不同故障模式。主库约束保护版本，文件哈希核对原件，索引可从已授权主记录重建。恢复顺序应先恢复主记录与治理账本，再恢复派生索引，最后开放访问。把向量库当唯一来源会同时损失原文、版本与可重建性。

选近似索引时，对相同向量集合先跑精确检索作为参照，再比较 Recall@K、过滤后的有效候选与尾延迟。近似搜索速度收益不能在未测召回损失时单独报告。[R09]

### 7.1.6 Graph Database

图数据库适合频繁的多跳关系查询，例如组件影响链或带角色约束的关联分析。收益来自明确关系结构，代价包括抽取、消歧、更新与一致性维护。

如果只有少量一跳关联，关系表可能已经足够。先用真实查询证明图遍历需求，再引入专用存储，不要仅为架构完整而复制一套数据。

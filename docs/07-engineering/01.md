# 7.1 数据库与持久化技术

## 要解决的问题

各种存储各自适合什么？

以主记录、原始对象和派生访问结构选择存储。默认先用关系库管理版本与事务，按实测需求引入其他引擎，避免为每个语义类别配一个数据库。

## 机制与细分考点

### 7.1.1 关系型数据库

关系库适合约束、事务和多维过滤，JSON 字段可容纳扩展，但不能用自由 JSON 代替所有索引和约束。

### 7.1.2 JSON / Document Store

Document Store 适合聚合文档与灵活字段；仍需制定版本、字段迁移和跨对象一致性方案，灵活不等于无模式。

### 7.1.3 Object Storage

Object Storage 保存原文件和大对象，主库记录哈希与定位；对象读权限、生命周期和删除任务必须纳入治理。

### 7.1.4 Event Store

Event Store 保存有序变化以支持重放，事件演进和投影重建需版本化；事件溯源会增加保留与删除复杂度。

#### 事件日志、当前表与向量索引

参考实现将原始表达事件追加保存，当前偏好表保存经过策略选择的视图，向量索引保存可重建的检索表示。更新偏好时，事件保留历史，当前表切换有效值，索引异步更新；读取当前值优先查表，避免索引延迟影响确定性属性。

这增加了数据协同成本，只有需要历史、更正或审计时才值得采用。Mem0 的追加路径与 LangGraph Store 的同键覆盖分别体现不同存储语义；二者都不能独立证明系统具有完整事件溯源能力。 [固定版本源码](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/mem0/memory/main.py#L918-L1098)。

### 7.1.5 Vector Database

Vector Store 支持相似搜索，是索引而非真值源。pgvector 官方支持精确搜索与近似索引，但过滤和召回表现仍需实测。[R09]

### 7.1.6 Graph Database

Graph Database 适合多跳关系遍历；若主要是有限依赖边，关系表也可能足够。先证明查询收益，再承担新系统运维。

## 推导与工程过程

主库、对象存储和索引有不同故障模式。主库约束保护版本，文件哈希核对原件，索引可从已授权主记录重建。恢复顺序应先恢复主记录与治理账本，再恢复派生索引，最后开放访问。把向量库当唯一来源会同时损失原文、版本与可重建性。

选近似索引时，对相同向量集合先跑精确检索作为参照，再比较 Recall@K、过滤后的有效候选与尾延迟。近似搜索速度收益不能在未测召回损失时单独报告。[R09]

## Atlas 案例

Atlas 可将对象和版本保存在 PostgreSQL，原始文件放对象存储，全文与向量作派生索引。此处没有容量或性能承诺。

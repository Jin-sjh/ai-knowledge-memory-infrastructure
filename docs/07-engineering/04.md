# 7.4 核心技术选型比较

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

选型如何比较而不变成排行榜？

将技术方案放入相同数据、模型、预算和任务中比较。问题类型、维护成本与失败代价比抽象的功能清单更有决策价值。

### 7.4.1 RAG vs Long Context

RAG 通过检索选择少量材料，长上下文倾向直接提供更完整输入。前者可能漏证据，后者可能增加成本、截断或使用困难，比较应基于同一可见来源和任务。

小而稳定的规范可先直接阅读；大规模变化资料再评估检索。固定预算比较与资源不限比较是两类实验，不能混成一个赢家结论。

### 7.4.2 RAG vs LLM Wiki

RAG 偏向从原始资料即时取证，Wiki 偏向预先整理主题解释。即时检索容易保持原文联系，预编译能减少重复整合，但要支付更新与验证成本。

来源变化频繁或需要精确引用时保留原文路径；概览问题多时可增加 Wiki 导航。两者可以组合，不必把页面摘要当成原始事实替代品。

### 7.4.3 Wiki vs Knowledge Graph

Wiki 强在连续叙述与解释，图强在明确关系与路径查询。问“如何理解发布流程”适合页面，问“组件变更影响哪些服务”可能适合图。

比较构建成本、覆盖和更新，而不是只看展示形式。图边与页面结论都需要来源；缺少治理时，两种表示都会保留看似完整的旧知识。

### 7.4.4 SQL vs Vector Search

SQL 适合明确条件与聚合，例如当前用户某属性、指定时间有效规则、审批人数计数。向量搜索适合目标未知或表达不确定的发现。

先按问题形态选择路径：已知主键不必语义检索，模糊经历也不宜强迫用户提供精确字段。联合访问可以先发现候选，再精确回查当前状态。

### 7.4.5 统一存储 vs 专用存储

统一存储减少同步与运维组件，专用存储可能更适合特定负载，但会增加跨系统一致性与删除传播责任。比较时列出主事实归属和派生重建方式。

小团队可先在一个可靠主库内划分逻辑模块；只有确认查询瓶颈后再增加专用索引。新增组件必须同时增加失败恢复与退出方案。

比较方案时先固定约束，再比较目标。例如必须零跨租户泄露、删除请求即时阻断、当前规则时态正确；满足这些约束的候选再按质量、延迟和总成本形成 Pareto 集。不能用更高平均问答分抵消访问泄露。

“统一存储更简单”也需要限定：同库简化事务和运维，但大型向量索引可能与业务写入争资源。应记录共享资源干扰并定义迁出触发，而不是永久坚持单库。

### 7.4.6 自建 Memory vs Memory Framework

#### 同一组业务契约怎样比较自建与框架

先固定四个输入：明确建立偏好、给出临时要求、长期更正、撤回偏好。各方案分别报告保存了哪些对象、下一次按什么读取、原记录是否仍进入上下文，以及撤回后哪些副本待处理。

自建方案可以用事件和当前档案实现；框架可能使用文本追加、同键覆盖或其他机制。都要接到相同可观察目标下比较，而不是要求内部数据一模一样。若框架自动提取却缺少当前视图，就把补建投影的工作计入接入成本；若自建省略提取，则不能把其确定性表现当作自动理解更准确。

再加入 API 超时和并发修改，观察是否重复保存或覆盖新状态。某方案首次调用很方便，失败恢复却需要大量适配，这也是实际复杂度。反过来，已成熟的框架适配若减少大量维护，不应因代码不是自己写就排除。

选型输出应是一份有前提的结论：它满足哪些硬约束、哪些能力由外部补齐、在什么负载下效果可接受，以及数据如何迁出。未经实验的质量、延迟和成本仍留空，不给主观产品排名。

LangGraph 官方包示例提供一个很小的可复现实验：覆盖同键、跨会话读取、恢复原线程及新建空 Store。它验证存储分工，不评价语义提取能力。因此不能用这两项单元测试给 Mem0 或其他提取框架排质量名次。[固定版本源码](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/store/memory.ts#L188-L219)。

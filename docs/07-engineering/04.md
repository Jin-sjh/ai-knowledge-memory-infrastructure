# 7.4 核心技术选型比较

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。核验日期：2026-11-13。

## 要解决的问题

选型如何比较而不变成排行榜？

将技术方案放入相同数据、模型、预算和任务中比较。问题类型、维护成本与失败代价比抽象的功能清单更有决策价值。

## 机制与细分考点

### 7.4.1 RAG vs Long Context

RAG 减少输入却可能漏证据；Long Context 保留更多原文却可能增加成本和干扰。比较时包含索引成本与输入预算。[R05]

### 7.4.2 RAG vs LLM Wiki

RAG 擅长按需选证据，Wiki 预先整理主题；Wiki 的构建和更新成本需摊入总成本，二者可以组合。

### 7.4.3 Wiki vs Knowledge Graph

Wiki 适合连续解释，Graph 适合结构关系与路径；选择依据读者任务，图谱不能自动替代可读论证。

### 7.4.4 SQL vs Vector Search

SQL 保证结构化约束与聚合，Vector Search 处理语义近邻。精确数值和时态过滤优先结构查询，模糊经历可用向量。

### 7.4.5 统一存储 vs 专用存储

统一存储简化事务与运维，专用存储可优化特定负载但增加同步、删除和故障恢复复杂度。

### 7.4.6 自建 Memory vs Memory Framework

自建便于控制契约与治理，框架缩短集成但带来依赖和策略黑盒。退出标准应包含数据导出与替换成本。

#### 把自建与框架放到同一契约下

先冻结偏好更正、跨用户隔离、删除与恢复四个输入序列，让候选方案交付相同的可观察结果，再比较工程量。自建方案至少需要来源、状态、错误处理和测试；框架方案也需要适配、权限和升级验证，不能只比较首个 API 调用的代码行数。

LangGraph 官方包示例提供一个很小的可复现实验：覆盖同键、跨会话读取、恢复原线程及新建空 Store。它验证存储分工，不评价语义提取能力。因此不能用这两项单元测试给 Mem0 或其他提取框架排质量名次。 [固定版本源码](https://github.com/langchain-ai/langgraphjs/blob/959f041dfb8f6bbafa6af3ebb4bc20484a9290da/libs/checkpoint/src/store/memory.ts#L188-L219)。

## 推导与工程过程

比较方案时先固定约束，再比较目标。例如必须零跨租户泄露、删除请求即时阻断、当前规则时态正确；满足这些约束的候选再按质量、延迟和总成本形成 Pareto 集。不能用更高平均问答分抵消访问泄露。

“统一存储更简单”也需要限定：同库简化事务和运维，但大型向量索引可能与业务写入争资源。应记录共享资源干扰并定义迁出触发，而不是永久坚持单库。

# 7.7 分阶段架构演进

[全书首页](../../README.md) · [本章导读](README.md)

> 概念说明与参考设计，非已实现系统报告。资料核验日期：2026-11-13。

## 要解决的问题

架构应按什么顺序演进？

先建立能验证语义与治理的最小闭环，再用测量暴露瓶颈。每一阶段都应有可回退基线，新增模块必须有独立收益证据。

### 7.7.1 MVP 最小实现

MVP 先打通一条受控路径：来源快照、明确规则读取、当前偏好、可解释回答和删除入口。选择少量真实需求，保留稳定身份与版本。

最小不是省掉权限和治理，而是减少自动化和表示种类。先用确定性路径检查事件变化，再逐步加入模型与检索，避免难以定位误差。

### 7.7.2 知识检索能力建设

知识检索阶段先建立原文与证据定位，测试错误码、条件跨块和旧版干扰等常见失败。按观察到的缺口增加混合通道或重排。

每次扩展保留相同回归集并记录成本。不要把一次答案更流畅当成检索改进，仍需核对必要证据是否进入输入。

### 7.7.3 长期记忆能力建设

长期记忆阶段先支持明确偏好的保存、更正与撤回，再扩展经历提炼。事件与当前视图要能解释用户何时改变要求、系统现在采用什么。

自动提取逐步开放，并保留候选与确认边界。没有更正和删除机制时，不宜让大量模糊对话直接进入长期默认。

### 7.7.4 Wiki / Graph 能力扩展

新增 Wiki 或图之前，指出当前哪类问题无法有效回答：主题概览需要反复整合，还是关系路径查询缺少结构。针对这类任务建设新表示并做对照。

同时增加来源依赖和更新测试。若收益不足，可以退出该视图而保留主事实，避免架构扩展成为不可撤回的数据复制。

### 7.7.5 服务拆分与规模化

#### 拆分索引服务前后分别检查什么

症状是假设性的：批量构建期间在线请求变慢。先测资源争用来自 CPU、内存、连接还是存储，再试工作队列和配额隔离；如果独立进程已满足目标，就未必需要独立网络服务。

决定拆分后，先定义任务输入版本、稳定事件身份和结果发布条件，保留一段双运行观察期：新服务构建候选索引，在线仍走已批准路径，对比对象覆盖和治理事件。不要让验证流同时执行真实副作用。

切换时确认来源、权限、删除账本和索引代际一致；回退时只切换派生访问路径，不恢复已撤销权限或已删除内容。新服务持续落后时，可以降级到受控精确访问，而不是继续返回过期结果。

扩容完成的证据应包括持续写入和删除下的追平、故障恢复及质量回归，而不只是查询吞吐。若维护能力跟不上，更多读取节点只会更快传播旧内容。

Letta Code 从提交快照编译记忆的做法，可启发分阶段发布：构建可读快照后再暴露给调用端。这里借鉴的是快照边界，不是建议把所有服务数据都存进 Git。大规模事件、高频写入与敏感数据治理仍需按工作负载选择存储。[R15][固定版本源码](https://github.com/letta-ai/letta-code/blob/bd31b0a72dfad1ba14fc3a82f47da6a2b606330d/src/backend/local/system-prompt-compilation.ts#L65-L198)。

每阶段应保留一条最简单可运行基线：确定性查询、全文或精确向量、带版本的直接引用。新增模块出错时可关闭改写、重排或主题视图，不必丢掉全部系统。回退不允许取消授权与删除检查。

规模化不仅是查询量增加，还包括更新频率、依赖扇出和删除积压。若离线维护吞吐跟不上，在线质量会逐渐下降，因此扩容评测必须同时加入持续写入和治理负载。
